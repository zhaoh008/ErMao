# ErMao 分章讲解

> 每一节的结构固定为：**课程要解决什么问题 → 本引擎怎么实现 → 亲手验证 → 与工业引擎的差距**。
> 建议对照代码阅读，文件名都写在每节开头。

---

## 1. 引擎循环与分层（第 1/2 讲）

**问题**：引擎不是"一个 Update"，而是**一组按依赖方向分层、每帧按固定顺序推进的系统**。
顺序错了会出现：输入延迟一帧、物理与渲染不同步、resize 时崩溃。

**实现**：`runtime/Application.cpp`

```cpp
Timer::Tick();                 // 1. 时间
Input::Update();               // 2. 输入快照（本帧不再变）
editor.Draw(...);              // 3. UI 先构建（决定鼠标是否被 UI 吃掉）
accumulator += dt;
while (accumulator >= 1/60) {  // 4. 固定步长仿真
    world.FixedUpdate(1/60);   //    物理
    accumulator -= 1/60;
}
world.Update(dt);              // 5. 可变步长逻辑（动画/AI/脚本）
world.BuildRenderScene(...);   // 6. 把场景翻译成渲染数据
renderer.Render(...);          // 7. 渲染
swapChain.Present(1);          // 8. 呈现
```

分层：

```
runtime → editor → gameplay(ai/physics/animation) → scene → renderer → rhi → core/platform
```

**关键边界**：`renderer` 只认识 `RenderScene`/`RenderItem`（网格 + 世界矩阵 + 材质参数），
不认识 `GameObject`。这条边界让"渲染"与"场景"可以独立演进——和 Piccolo 的做法一致。

**验证**：
- 启动日志依次出现 Window/Device/Renderer/Assets/World/Editor；
- 把 `FixedUpdate` 的步长改成 1/10，Play 后小球会明显穿地（步长过大导致隧穿）——这就是"固定步长为什么是 1/60"。

**差距**：UE 用 TaskGraph 把 tick 拆成并行任务；Piccolo 有专门的 tick 函数注册表。ErMao 是显式顺序调用，简单但不可扩展。

## 2. 游戏世界：对象模型、反射与序列化（第 3 讲）

**问题**：怎么用数据描述"世界"？怎么让编辑器、存档、运行时共享同一份描述？

**实现**：`scene/`

1. **GameObject = 名字 + 层级 Transform + 一组 Component**
   - `Transform` 用四元数（避免万向锁），`WorldMatrix = Parent.WorldMatrix * LocalMatrix`
   - 对象所有权统一在 `World::m_objects`（`vector<unique_ptr<GameObject>>`）
   - **踩过的坑**：一开始让父节点持有子节点的 `unique_ptr`，结果 `CreateGameObject(name, parent)` 里局部 `unique_ptr` 析构，父节点留下悬垂指针 → 随机崩溃。现在的规则是"World 拥有全部对象，父子只存裸指针"。

2. **反射**：每个组件在 .cpp 里写一个 `Describe(TypeInfo&)`，用**成员指针**注册字段：

```cpp
void MeshRenderer::Describe(TypeInfo& t) {
    t.factory = [](GameObject* go) -> Component* { return go->AddComponent<MeshRenderer>(); };
    t.Field("albedo",    FieldType::Color, &MeshRenderer::albedo,    "基础色");
    t.Field("roughness", FieldType::Float, &MeshRenderer::roughness, "粗糙度", 0.04f, 1.0f);
}
```

   为什么用成员指针而不是 `offsetof`？因为组件有虚函数，不是 standard-layout，`offsetof` 是条件支持行为；成员指针 + `std::function<void*(void*)>` 访问器既标准又能带类型。

3. **一份元数据，三处消费**：
   - Inspector：`field.access(comp)` 拿到 `void*`，按 `FieldType` 生成控件；
   - 序列化：同样的 switch 写进 JSON；
   - 反序列化：`TypeInfo::factory` 造组件，再按字段名回填。

**验证**：编辑器里改物体颜色 → `Save` → 退出 → 重开 `Load`，颜色、父子关系、组件参数完全一致。
打开 `build/bin/assets/scenes/demo.ermao.json` 能直接读懂结构。

**差距**：UE 有 UHT 生成 `.generated.h`；Piccolo 用 entt 的反射宏。ErMao 是手写 Describe，优点是零构建步骤，缺点是新增字段要记得写一行。

## 3. 渲染管线：设备、相机、实例化、剔除（第 4/7 讲）

**问题**：怎样把"一堆物体"高效变成"屏幕像素"？

**实现**：`rhi/Device`、`renderer/Renderer`

**步骤 1：坐标系与投影**（`core/Math.h`）

右手系、相机看 -Z、深度映射到 [0,1]：

```
yScale = 1/tan(fov/2)
m[2][2] = far/(near-far)   m[2][3] = -1   m[3][2] = near*far/(near-far)
```

`Mat4` 是**列主序**（`m[col][row]`），与 HLSL 常量缓冲默认布局一致，可以直接 `memcpy`，不需要转置。

**步骤 2：批处理**（`Renderer::BuildBatches`）

1. 视锥剔除：把网格局部 AABB 的 8 个角点变换到世界空间，再用 6 个平面做 p-vertex 测试；
2. 按 `(mesh, texture)` 排序分组；
3. 每个物体压成 96 字节的 `InstanceVertex`（4 列世界矩阵 + 颜色 + 材质参数）上传到动态 VB；
4. 每组一次 `DrawIndexedInstanced`。

```cpp
// 实例矩阵在 VS 里用「列」拼装，再乘行向量，等价于 W * v
float4x4 W = float4x4(col0, col1, col2, col3);
float4 worldPos = mul(float4(pos, 1.0), W);
```

**步骤 3：Pass 顺序**（`Renderer::Render`）

```
Shadow(2048²) → Sky(全屏) → Opaque(实例化) → Debug(线) → Post(ACES) → UI
```

**验证**：`F1` 看 Stats：27 个物体、绘制调用 ~12 次（阴影 6 + 天空 1 + 不透明 4 + 后处理 1），
说明合批生效了。把 `BuildBatches` 里的分组条件去掉，draw call 会变成每个物体一次。

**差距**：工业引擎会做 GPU 剔除 + 间接绘制 + 材质排序；这里 CPU 剔除 + 简单分组已经能讲清原理。

## 4. 光照与材质：GGX（第 5 讲）

**问题**：怎样让"粗糙的木头"和"光滑的金属"在同一个光照模型下都可信？

**实现**：`engine/shaders/PBR.hlsl`

Cook-Torrance 三项：

$$
f_r = \frac{D(h)\,G(l,v)\,F(v,h)}{4 (n\cdot l)(n\cdot v)}
$$

- **D（GGX 法线分布）**：`a = roughness²`，`D = a² / (π ((n·h)²(a²-1)+1)²)`
- **G（Smith-Schlick 几何项）**：`k = (r+1)²/8`，`G = (n·l)/((n·l)(1-k)+k) · (n·v)/((n·v)(1-k)+k)`
- **F（Schlick 菲涅尔）**：`F = F0 + (1-F0)(1-v·h)^5`，电介质 `F0=0.04`，金属用 albedo 当 F0

```hlsl
float3 kd = (1.0 - F) * (1.0 - metallic);              // 金属没有漫反射
float3 specular = (D * G * F) / (4.0 * NdotV * NdotL);
return (kd * albedo / PI + specular) * radiance * NdotL;
```

再加半球环境光（天光/地光 lerp）作为廉价 GI，最终 `color += albedo * emissive`。

**颜色空间**：贴图是 `R8G8B8A8_UNORM_SRGB`，采样时硬件自动转线性；材质的 albedo 直接按线性值用。
**踩过的坑**：一开始在 shader 里又做了一次 `pow(color, 2.2)`，地面黑得几乎看不见——双重 gamma 解码。

**验证**：Inspector 里把球体的 roughness 从 0.12 拖到 0.9，高光从"一个小亮点"变成"整片柔光"；
metallic 拖到 1，漫反射消失、只剩环境反射的高光。

**差距**：没有 IBL（用环境贴图做镜面反射）、没有法线贴图、没有多散射 GGX。

## 5. 阴影（第 5/7 讲）

**问题**：如何在实时渲染里得到方向光的投影？

**实现**：`Renderer::ShadowPass` + `ComputeLightMatrix` + `SampleShadow`

1. **光源相机**：`eye = focus + sunDir * distance`，`LookAt(eye, focus, up)`，正交投影 `[-r, r]`。
   ⚠️ 符号写反会让相机跑到物体背面，阴影全错——我在调试时正是通过"阴影贴图可视化"（`F3` 到 5）发现物体只占中间一小块。
2. **深度 Pass**：只写深度，`CullMode = NONE` + 光栅化 `DepthBias`；
3. **采样**：世界坐标乘 `lightViewProj` → NDC → `uv = (x*0.5+0.5, 0.5-y*0.5)`（y 翻转）→ 3×3 PCF；
4. **Bias**：深度偏移 0.0025 + 沿法线偏移 0.035，消除自阴影条纹（acne）。

```hlsl
float4 lightClip = mul(gLightViewProj, float4(worldPos + N * normalBias, 1.0));
float3 ndc = lightClip.xyz / lightClip.w;
float2 uv  = float2(ndc.x * 0.5 + 0.5, -ndc.y * 0.5 + 0.5);
```

**验证**：`F3` 连按到阴影视图，地面上的亮/暗就是 shadow factor（0/1）；
`F4` 关阴影，对比物体与地面的接触感。

**差距**：单级联、无 PCSS 软阴影、无点光源阴影（立方体贴图）。

## 6. 天空与后处理（第 6/7 讲）

**天空**（`Sky.hlsl`）：不贴天空盒，直接**全屏三角形 + 逆 ViewProj 重建视线**：

```hlsl
float4 world = mul(gInvViewProj, float4(ndc, 1.0, 1.0));
world.xyz /= world.w;
float3 dir = normalize(world.xyz - cameraPos);
```

然后按 `dir.y` 做地平线到天顶的渐变，叠加太阳盘（`smoothstep(0.9995, 0.99985, dot(dir, sunDir))`）与两级光晕。

**后处理**（`Post.hlsl`）：场景先渲染到 `RGBA16F`，再 ACES 色调映射 + gamma + 暗角，输出到 LDR 后备缓冲。
ACES 的好处是高光不会"死白"，而是自然过渡到白色。

**验证**：`F3` 到 3（基础色）可以看到 HDR 目标确实保留了 >1 的亮度（太阳），
关掉 Post 直接输出会过曝——这就是 HDR 中间缓冲的意义。

## 7. 动画：关键帧与采样（第 8 讲）

**问题**：怎样用最少的存储让角色/机关动起来？

**实现**：`animation/Animation.h/.cpp`

```cpp
struct TransformKey { float time; Vec3 position; Quat rotation; Vec3 scale; };
struct NodeTrack    { std::string target; std::vector<TransformKey> keys; };
```

采样流程：
1. `t = fmod(time, duration)`（循环）；
2. 查区间 `[k_i, k_{i+1}]`；
3. `alpha = (t - k_i.time) / (k_{i+1}.time - k_i.time)`；
4. 位置线性、旋转 `Slerp`、缩放线性；
5. 写回目标子对象的**局部**变换。

```cpp
position = Lerp(key->position, next.position, alpha);
rotation = Quat::Slerp(key->rotation, next.rotation, alpha);
```

**演示场景**：
- `风车机关` → 子节点 `风车叶片` 绕 Y 匀速旋转（90°/s，4s 一圈），`风车吊舱` 是叶片的子节点，自然跟随；
- `浮动水晶` → 子节点在 Y 上做正弦浮动 + 缓慢自转。

**验证**：Inspector 里把 `speed` 改成 2，动画立刻加速；把 `playing` 取消勾选，动画停止。

**差距**：**没有蒙皮**。蒙皮需要：
1. 顶点加 `BLENDINDICES`/`BLENDWEIGHT`；
2. 骨骼层级 → 每帧算 `boneMatrix[i] = boneWorld[i] * inverseBind[i]`；
3. VS 里 `skinned = Σ w_i * boneMatrix[idx_i] * position`。
采样器（上面的 1–4 步）可以原样复用，只是把"写回 GameObject"换成"写进骨骼调色板"。

## 8. 物理（第 10/11 讲）

**问题**：怎样让物体按物理规律运动、并且不穿地？

**实现**：`physics/PhysicsWorld.cpp`

1. **积分**：半隐式欧拉
```cpp
velocity += gravity * dt;
position += velocity * dt;
```
2. **碰撞检测**：
   - 球-球：`dist < r1+r2`，法线 = 归一化中心差；
   - 球-AABB：先求最近点 `clamp(center, min, max)`，若球心在盒内则沿最小穿透轴推出；
   - 盒-盒：AABB 重叠，沿最小重叠轴推出（轴对齐近似）。
3. **求解**：位置修正 + 法向冲量 `j = -(1+e)·v_n / (1/m1 + 1/m2)`，切向乘摩擦系数；
4. **休眠**：贴地且速度平方 < 0.02 持续 0.6s → 速度清零；
5. **迭代 4 次**，让多接触点更稳定。

**验证**：Play 后 6 个球从不同高度落下，弹跳高度逐次衰减；
`F6` 打开碰撞体线框，能看到球体与静态木箱的接触。把 `restitution` 改成 1.0，球会一直弹（最终因阻尼停下）。

**差距**：没有 GJK/EPA（凸体精确碰撞）、没有 CCD（高速穿透）、没有关节/布料/破坏。

## 9. 编辑器与工具链（第 13/14 讲）

**问题**：引擎的"易用性"几乎全在工具链上。编辑器怎么和运行时共享数据？

**实现**：`editor/`

- **即时模式 UI**：没有控件树，每帧重画；只有 `hotId`（悬停）与 `activeId`（拖拽中）两个状态。
- **布局**：面板内一个垂直游标 `m_cursorY`，`RowRect()` 分配一行；标签列固定宽度，控件占剩余。
- **字体**：GDI 把字符画进 DIB，再拷进 1024² 图集；ASCII 用 Consolas，中文回退微软雅黑；新字符按需光栅化、只更新对应的 `D3D11_BOX` 区域。
- **反射驱动检视器**：遍历 `TypeInfo::fields`，`FieldType` → 控件（浮点=拖动条，颜色=色块+RGB，网格=下拉框）。
- **拾取**：屏幕点 → `Camera::ScreenToRay` → 与每个物体的世界 AABB 求交，取最近。
- **Play-In-Editor**：Play 前 `world.ToJson().Dump()` 存字符串；Stop 时 `JsonValue::Parse` 后 `world.FromJson` 回滚。

**验证**：
1. 左键点木箱 → Inspector 出现它的所有组件；
2. 改颜色，画面实时变化；
3. Play → 球开始下落 → Stop → 球回到初始位置（快照回滚）；
4. 控制台能看到 `选中: 木箱_0`、`Editor: Play` 等日志。

**差距**：没有 gizmo（用 Inspector 数值代替）、没有撤销栈、没有资源浏览器、没有多窗口 docking。

## 10. AI：导航、A\*、感知（第 16 讲）

**问题**：怪物怎么"知道"该往哪走、该不该追？

**实现**：`ai/NavGrid.cpp`、`ai/Agents.cpp`

1. **栅格化**：XZ 平面 0.5m/格；静态盒的 footprint 按角色半径（0.45m）膨胀后标记为阻挡；世界边缘一圈设为墙。
2. **A\***：
   - `g` = 起点距离，`h` = 八方向启发式 `(dx+dz) + (√2-2)·min(dx,dz)`（可采纳）；
   - 开表用 `priority_queue`（二叉堆），闭表用 `u8` 数组；
   - 对角移动时检查两个相邻正交格，禁止"贴角穿越"；
   - 回溯后做**视线拉直**（`HasLineOfSight` + 贪心跳点）。
3. **状态机**：`巡逻`（随机点）↔ `追击`（玩家在视野内）。
4. **感知**：距离 + FOV 余弦 + 栅格视线遮挡（墙体后看不见）。

```cpp
state = CanSeePlayer(world, playerPos) ? 1 : 0;
if (state == 1 && repathTimer <= 0) { RequestPath(world, playerPos); }
```

**验证**：Play 后站着不动，小怪会绕开木箱走过来（路径不是直线）；`F6` 能看到绿色路径点与黄色视野锥；
走到箱子后面，小怪丢失目标、回到巡逻。

**差距**：没有 NavMesh（多边形）、没有行为树/GOAP、没有群体避障（RVO）。

## 11. 并行：Job System（第 20 讲）

**问题**：单核频率上不去，怎么把 CPU 吃满？

**实现**：`core/JobSystem.cpp`

```cpp
// 分块 + 原子抢块 + join
std::atomic<u32> nextChunk{0};
auto worker = [&] {
    for (;;) {
        const u32 i = nextChunk.fetch_add(1);
        if (i >= chunks) break;
        rangeBody(begin + i*chunkSize, min(begin + (i+1)*chunkSize, end));
    }
};
```

- 主线程也参与工作（否则"只等不干"，加速比打折）；
- 视锥剔除用它并行化（`Renderer::BuildBatches`）；
- Stats 面板有"CPU 基准"：100 万次 `sqrt/sin/cos`，串行 vs 并行，直接看加速比。

**验证**：点 Stats 里的基准按钮，8 核机器上通常能看到 4–6x；受限于内存带宽与主线程参与比例，不会线性。

**取舍（重要）**：这里是"每次调用临时起线程"，比常驻线程池多了几十微秒创建开销，但完全没有唤醒丢失/生命周期风险。
我第一版写的是常驻线程池，但在 `Init/Shutdown` 附近出现了非确定性崩溃（后来定位是场景对象所有权 bug，不是线程池），
为了教学可靠性改成了现在的模型。工业引擎会用常驻池 + fiber 依赖图 + 无锁队列。

## 12. 一次完整的调试故事（建议按这个顺序读代码）

1. **窗口是黑的** → 检查 `Device::BeginFrame` 是否清了 `RTV`、`Render` 是否在 Post 前切回 backbuffer；
2. **物体消失** → 绕序：右手系 CCW 正面，`FrontCounterClockwise = TRUE`；调试时先关剔除；
3. **颜色发橙** → 截图编码：WIC 把格式协商成 BGRA，自己写的 RGBA 数据就红蓝互换；
4. **地面全黑** → 双重 gamma：sRGB 贴图已解码，shader 里又 `pow(2.2)`；
5. **影子不对** → 光源相机方向写反；用"阴影贴图可视化"确认物体在不在画面里；
6. **随机崩溃** → 父子对象的所有权：子节点被局部 `unique_ptr` 提前释放。

这六条基本覆盖了"从零写一个小引擎"最容易卡住的地方，也是我在这个项目里真实踩过的坑。
