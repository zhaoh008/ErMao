## 0. 本讲地图

- **现象/最简实现**：改窗口或换后端为何不该动玩法；两个模块互相 include 会怎样；先给“高层调低层”的两层结构。
- **具体失败**：头文件循环、改一个结构体引发连锁重编、渲染器离不开 D3D 因而无法单测。
- **正式方案**：单向依赖、稳定接口、数据流；先讲数据和调用，再给“分层/渲染硬件接口（RHI）/数据传输对象（DTO）”这些名字。
- **源码核对与诚实结论**：本工程只有一个静态库，目录分层靠约定；`scene` 反向依赖 `game/ai/physics/renderer` 的数据类型。

## 1. 先看现象：两个能直接观察到的问题

**问题 A：改窗口或换后端，为什么不该动玩法代码？**
如果玩法代码里直接写 `ID3D11Device*`、创建缓冲、调用 `Present`，那么换 Vulkan、做无渲染服务器、
写一个只跑逻辑的单元测试，都得改玩法。这不是“代码不好看”，而是**同一段逻辑被绑死在某个图形 API 上**。

**问题 B：两个模块互相 include 会怎样？**
假设 `renderer/Renderer.h` 为了方便直接 `#include "scene/World.h"`，而 `scene/World.h` 又
`#include "renderer/Renderer.h"`。无论先编译哪个 `.cpp`，总有一边在展开时看不到另一边的完整类型，
报“未定义的类型/不是类名”，或者只能靠前向声明拿到指针、拿不到成员。`#pragma once` 只防止**同一个头文件重复展开**，
不解决**互相需要完整定义**。

本工程现在的真实状态是“基本单向，但有几条反向边”；下面先给最简结构，再逐条对照源码。

## 2. 最简单、能工作的两层结构

先只考虑“游戏世界”和“渲染器”两个模块。最省事的写法是让渲染器直接拿 `World*`：

**概念伪代码：渲染器直接读 World（能跑，但耦合）**

```cpp
// renderer/Renderer.h
#include "scene/World.h"
class Renderer {
public:
    void Render(World& world) {
        for (GameObject* o : world.RootObjects())
            if (auto* mr = o->GetComponent<MeshRenderer>()) Draw(mr->mesh, o->WorldMatrix(), mr->albedo);
    }
};
```

**概念伪代码：先抽出一份扁平数据**

```cpp
// renderer/RenderScene.h
struct RenderItem { const Mesh* mesh; Mat4 world; Vec4 albedo; /* ... */ };
struct RenderScene { std::vector<RenderItem> items; /* 灯光、粒子、精灵 */ };

// scene/World.cpp
void World::BuildRenderScene(RenderScene& scene, const Camera& camera) const {
    for (GameObject* root : m_roots) root->ForEach([&](GameObject* o) {
        if (auto* mr = o->GetComponent<MeshRenderer>()) {
            scene.items.push_back({mr->mesh, o->WorldMatrix(), mr->albedo, /* ... */});
        }
    });
}

// renderer/Renderer.cpp：只读 RenderScene
void Renderer::Render(const Camera& camera, const RenderScene& scene, float time, bool wireframe) {
    RenderInternal(camera, scene, time, wireframe, ...);
}
```

两层的最小规则只有一句：**低层不 include 高层；高层可以 include 低层。**
调用方向是“高层 → 低层”，数据方向是“高层把数据整理好，低层只读”。

在本工程里，这个“数据契约”就是 `RenderScene`。`Renderer` 的实现不认识 `World`、`GameObject`、`Component`；
它只认 `RenderItem`、`PointLightRender`、`SkinnedDraw` 等扁平结构。好处很直接：

- 渲染器不再依赖 `World` 的数据形状（手工填一个 `RenderScene`；仍需要 D3D 设备才能实例化，见 §3.3）；
- 玩法层不必知道实例缓冲、批处理、阴影图；
- 将来改批处理/GPU Driven，`World::BuildRenderScene` 的输出不变（[第 22 讲](L22-GPU%20Driven.md)）。

但“能跑”不等于“分层正确”。下面看三个具体失败。

## 3. 让最简结构具体失败

### 3.1 失败一：头文件循环，编译期就炸

**概念伪代码：互相 include**

```cpp
// A.h
#pragma once
#include "B.h"
struct A { B b; };   // 需要 B 的完整定义

// B.h
#pragma once
#include "A.h"
struct B { A a; };   // 需要 A 的完整定义
```

先展开 `A.h`：它 include `B.h`；`B.h` 再 include `A.h` 时被 `#pragma once` 跳过，于是 `B.h` 里看不到 `A` 的定义，
`struct B { A a; };` 编译失败。反过来先展开 `B.h` 也一样。这不是“编译器脾气坏”，而是**两个类型互相按值包含在逻辑上不可能同时成立**。

可行的修法只有两类：

1. **打破环**：把其中一个方向的依赖改成指针/引用 + 前向声明（`struct A;`），并且不在头文件里访问成员；
2. **抽接口**：把双方都需要的东西下沉到更低层（例如把 `RenderScene` 放到独立的数据层），让两边都依赖它。

注意：前向声明只能解决“指针/引用/函数参数”，不能解决“按值成员”“继承”“内联调用成员函数”。所以它不是万能的。

### 3.2 失败二：改一个结构体，重编一大片

本工程是**一个静态库**：

**源码节选：`CMakeLists.txt`（用 `...` 省略了绝对路径）**

```cmake
file(GLOB_RECURSE ERMAO_ENGINE_SOURCES CONFIGURE_DEPENDS .../engine/src/*.cpp)
list(REMOVE_ITEM ERMAO_ENGINE_SOURCES .../runtime/main.cpp)
add_library(ErMaoEngine STATIC ${ERMAO_ENGINE_SOURCES})
```

也就是说，`engine/src/` 下的 `core/rhi/renderer/scene/game/editor/runtime` 全在**同一个 target** 里，
CMake 不会阻止 `scene` include `game`，也不会因为“越层”报错。目录是约定，不是编译期约束。

改 `renderer/RenderScene.h` 里的一个字段，所有直接/间接包含它的翻译单元都要重编。按当前源码静态统计：

- 直接 `#include "renderer/RenderScene.h"` 的文件有 **9 个**（`renderer/Renderer.h`、`scene/World.h`、
  `game/*` 的 6 个文件、`runtime/Engine.h`）；
- 直接 `#include "scene/World.h"` 的文件有 **19 个**（`ai/`、`game/`、`physics/`、`editor/`、`runtime/`、`scene/` 都有）。

这不是“编译慢一点”的小事：它意味着一个渲染数据结构的改动会把玩法、AI、物理、编辑器的编译一起拖下水。
真正的分层构建会给每层独立 target、只暴露必要的公共头；本工程为了教学和构建简单，没有这么做。

### 3.3 失败三：渲染器离不开 D3D，单测/换后端都难

`Renderer::Init(Device* device)` 直接拿具体的 `Device`；`Device` 又暴露 `ID3D11Device*`、`ID3D11DeviceContext*`。
`Renderer::ViewportTexture()` 返回裸 `ID3D11ShaderResourceView*`，编辑器直接把它塞给 `ImGui::Image`。
所以：

- 没有 GPU/Windows 时，`Renderer` 的绝大多数逻辑无法实例化；
- 想单测 `BuildBatches` 的剔除/分批，也得先造一个 D3D11 设备；
- “换后端只改 rhi”在接口层面不成立：渲染器和编辑器都直接写了 D3D 类型。

本工程确实有一个 `rhi/VulkanBackend.*`，但它只是**阶段一**：实例、设备、交换链、画一个三角形并截图，
**没有接进 `Renderer` 的 Pass**。所以不能宣称“把 rhi 换成 Vulkan，renderer 以上不用动”。
另外仓库当前没有测试工程；“可以给 `core/Math` 写单测”是**能力**，不是**已存在的事实**。

## 4. 正式方案：依赖方向、接口、数据流

把上面的失败反过来，就是三条工程规则。

### 4.1 依赖方向：源代码的 include 边必须构成有向无环图

把模块看成点，把“A include B”看成 A → B 的边。要求这个图是**有向无环图（DAG）**，并且边的方向与“抽象层次”一致：
低层不依赖高层。常见顺序是：

**示意：允许的依赖方向（上层依赖下层）**

```
runtime / editor          （组装、工具，最高层）
      ↓
game / ai / physics / animation
      ↓
scene                     （World / GameObject / Component）
      ↓
renderer                  （Camera / Mesh / RenderScene / Renderer）
      ↓
rhi                       （Device / Buffer / Texture / Shader）
      ↓
core                      （Math / JSON / Log / Timer / JobSystem）
```

“高层”可以调用“低层”，但“低层”的头文件里不能出现“高层”的类型。这样低层可以单独编译、单独测试、被多个高层复用。
代价是：高层需要的数据要**下沉**成低层能理解的形状，或者通过接口/回调在运行时注入。

### 4.2 接口：把“我需要什么数据”与“你怎么实现”分开

`RenderScene` 是一个**数据传输对象（Data Transfer Object，DTO）**：它只描述“这一帧要画什么”，
不包含“怎么画”。`Renderer` 依赖这个 DTO，而不是依赖 `World`。同样，如果要做真正的后端抽象，
应该让 `Renderer` 依赖 `IDevice`/`IRenderBackend` 这类接口，而不是 `ID3D11Device*`。

判断一个接口是否真的解耦，看两个问题：

1. 低层头文件里有没有出现高层的具体类型？（有 → 没解耦）
2. 换实现时，调用方要不要改 include/编译？（要 → 没解耦）

### 4.3 数据流：每帧一份“渲染输入”，只读不改

**示意：每帧数据流**

```
输入 → World（组件更新/物理/AI/动画） → RenderScene → Renderer → GPU
```

`World::BuildRenderScene` 负责把“实体 + 组件”翻译成“网格 + 世界矩阵 + 材质参数”；
`Renderer::BuildBatches` 负责剔除、排序、填实例数据；`DrawBatches` 只负责绑缓冲和 draw。
每一段只做一件事，数据形状在边界上固定下来。

**代价与替代方案**：`RenderScene` 每帧要拷贝/重建一次（本工程复用 `m_scene` 减少堆分配），
指针只在你保证生命周期时才能用；直接传 `World*` 省拷贝，但回到 3.1 的耦合。

## 5. 回到本仓库：真实 include 与妥协

### 5.1 哪些说法是真的

**源码节选：`renderer/Renderer.h` 的 include**

```cpp
#include "core/Math.h"
#include "core/Types.h"
#include "renderer/Camera.h"
#include "renderer/DebugDraw.h"
#include "renderer/RenderScene.h"
#include "renderer/SkinnedMesh.h"
#include "rhi/Buffer.h"
#include "rhi/Device.h"
#include "rhi/RenderTarget.h"
#include "rhi/Shader.h"
```

确实**没有** `scene/World.h`，也没有 `game/`。`Renderer` 的实现只吃 `RenderScene`。`scene/World.h` 里也没有
`d3d11.h`；`core/` 下没有任何 D3D 头。这些是分层有效的部分。

**源码节选：`renderer/RenderScene.h`（说明它确实是扁平数据）**：`RenderItem` 只有 `mesh`、`world`、`albedo`、
`roughness/metallic/emissive/uvScale`、`baseColor`、`castShadow`；`RenderScene` 只有若干 `std::vector`（`items`、`skinned`、
`pointLights`、`particles`、`sprites`、`healthBars`）加 `is2D`/`camera2D` 与太阳/环境光/阴影参数，没有 `World`/`GameObject` 成员。

### 5.2 哪些地方方向反了（必须诚实）

| 真实依赖（源码证据） | 方向问题 | 后果 |
|---|---|---|
| `scene/World.h` include `ai/NavGrid.h`、`renderer/Camera.h`、`renderer/RenderScene.h`；`scene/World.cpp` include 4 个 `game/*.h` 并注册组件 | scene → ai/renderer/game 反向 | `World` 不能脱离这些头单独编译；改玩法组件会重编 `World.cpp`；scene 复用必须带上 game |
| `scene/Components.h` include `renderer/Camera.h`（`CameraComponent` 持有 `Camera`） | scene → renderer | 组件层依赖渲染相机类型 |
| `renderer/SkinnedMesh.h` include `animation/Skeleton.h` | renderer → animation | 与 `animation → scene → renderer` 形成**模块级环**（文件级未成环，但目录级已成环） |
| `renderer/Camera.cpp` include `platform/Input.h`（`Camera::UpdateFly` 直接读键盘）；`editor/EditorUI.cpp` include `runtime/Packager.h`，`runtime/Engine.h` include `editor/EditorUI.h` | renderer → platform；editor ↔ runtime | 相机把编辑器飞行混进渲染模块；editor/runtime 模块级环（头文件没成环只因 `Packager.h` 很薄） |
| `rhi/Device.cpp` include `platform/Window.h`；`Device::Init(Window*)` | rhi → platform | RHI 不是纯图形抽象，窗口系统被绑进来 |
| `Renderer::ViewportTexture()` 返回 `ID3D11ShaderResourceView*`，`EditorUI.cpp` 直接 `ImGui::Image` | 具体 D3D 类型穿透到编辑器 | 换后端要改编辑器 |
| `CMakeLists.txt` 只建一个 `ErMaoEngine` 静态库 | 构建期不强制分层 | 任何目录都能 include 任何目录，越层不会报错 |
| `rhi/VulkanBackend.*` 只有阶段一，未接 `Renderer` | 声称的“可换后端”未落地 | 不能把 Vulkan 当作已有的后端替换证明 |

所以更准确的图是“**一条主方向 + 若干反向边**”：

```
core ← rhi ← renderer ← scene ← game/ai/physics/animation
  ↑                ↑         │
  └── platform ────┘         └──→ game（World.cpp 注册）
editor ↔ runtime（互相 include，模块级环）
```

`scene/World.h` 里没有 `d3d11.h`，但它有 `renderer/Camera.h`；`renderer/Renderer.h` 里没有 `scene/`，
但 `renderer/SkinnedMesh.h` 有 `animation/Skeleton.h`。**“某一层没有直接 include 最高层”不等于“分层干净”**，
要看整条传递闭包。

## 6. 一个数据流例子：一个立方体从 World 到 draw

设场景里有一个带 `MeshRenderer` 的立方体，`mesh = "cube"`，`albedo = (0.8, 0.8, 0.82, 1)`，世界矩阵为 `M`。

| 阶段 | 代码位置 | 数据变化 |
|---|---|---|
| 玩法/场景 | `GameObject` 的 `m_position/m_rotation/m_scale` | 物体摆好；`WorldMatrix()` 得到 `M` |
| 翻译 | `World::BuildRenderScene` | 读 `MeshRenderer`，填 `RenderItem{mesh, M, albedo, roughness, ...}`，push 进 `scene.items` |
| 剔除 | `Renderer::BuildBatches` | 用 `camera.GetFrustum()` 与网格局部 AABB 变换后的世界 AABB 判断；不可见则 `++culled` |
| 分批 | 同上 | 按 `(mesh Id, texture Id)` 排序；同网格同贴图进同一 `Batch`；`InstanceVertex` 填世界矩阵 4 列 + 法线矩阵 3 列 + 材质 |
| 提交 | `Renderer::DrawBatches` | 绑 slot0 网格 + slot1 实例，`DrawIndexedInstanced(IndexCount, batch.count, ...)` |
| GPU | `PBR.hlsl` | `worldPos = M*p`，`clip = gViewProj*worldPos`，PS 算法线/光照 |

这条链路里，`World` 不知道 `DrawIndexedInstanced`，`Renderer` 不知道 `GameObject`。
中间唯一的共同语言是 `RenderScene`。如果哪天把 `RenderItem` 改成 SoA（`std::vector<Mat4> worlds`），
`World::BuildRenderScene` 和 `Renderer::BuildBatches` 都要改，但 `GameObject`/组件/玩法可以不动——这就是边界的价值。

若只是加前向声明 `class World;` 并把成员改成指针，可能编过，但依赖方向已经反了。不要把“编过”当成“分层正确”。

## 8. 自测题

1. 如果 `Renderer` 直接 include `World`，会破坏哪条性质？为什么“能编过”不是充分条件？
2. `RenderScene` 为什么要拷贝/重建数据，而不是直接传 `World*`？代价是什么？
3. 本工程 `scene → game` 的反向依赖具体在哪几处 include/注册？怎么消除？
4. `#pragma once` 能解决互相 include 吗？前向声明能解决所有情况吗？
5. 为什么“只有一个静态库”会让分层更容易退化？

**答案**

1. 破坏“低层不依赖高层”：`renderer` 会依赖 `scene` 的具体类型，无法脱离场景编译/测试；能编过只说明当前 include 顺序碰巧可行，
   换一个入口或改成员布局就可能失败。
2. `RenderScene` 是稳定的 DTO，渲染器只读它，因而能在没有 `World` 时构造测试；代价是每帧拷贝/重建 vector、指针生命周期需保证。
   本工程用 `Engine::m_scene` 复用对象减少分配。
3. `scene/World.cpp` 顶部 include `game/ThirdPersonController.h`、`ParticleEmitter.h`、`SkinnedCharacter.h`、`WaveGame.h`，
   并在 `World::Init` 里 `RegisterAllComponents/RegisterAgentComponents` 注册。消除办法：把注册移到 `runtime`/`game` 初始化，
   `World` 只暴露 `RegisterComponent<T>`；或把内置组件下沉到独立 `components` 层。
4. 不能。`#pragma once` 只防止同一头文件重复展开，不打破“互相需要完整定义”的环。前向声明只适用于指针/引用/参数，
   不适用于按值成员、继承、内联访问成员。
5. 因为编译期没有 target 边界，任何目录都能 include 任何目录；越层不会报错，只会在 code review 时靠人发现。
   独立的层 target 可以把“允许的 include”变成构建系统约束。
