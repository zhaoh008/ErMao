# 第 18–19 讲：网络基础与同步

> 对应 GAMES104 第 18/19 讲（网络）。
> 状态：**引擎级网络层已实现**（`engine/src/net/`，见第 10 节与本篇末尾的源码入口）。
> 本讲仍按“现象 → 最简实现 → 失败场景 → 正式方案”讲原理；源码实现是主机权威 +
> 快照插值 + 轻量预测校正，不是 rollback。
> 本讲会同时出现“客户端预测校正”和“回滚（rollback）”，它们是两件事，第 6 节有对照表。

## 1. 现象：两个屏幕上的位置不一样

A、B 在同一个房间里对战：A 屏幕上 B 站在箱子左边，A 瞄准开枪；
B 屏幕上自己已经绕到箱子右边，看到 A 的枪口指向空处。A 的客户端判“命中”，
B 的客户端判“没中”。

两台机器各自有一个世界，各自按自己的帧率推进。A 的输入要过一段时间才到 B，B 在收到之前
只能继续用旧信息模拟 A。**“我看到的位置”和“对方此刻的位置”本来就不是同一时刻的量。**

本讲回答：怎样让两台机器对“现在发生了什么”达成足够一致的看法，同时让本地手感不因延迟变差。

## 2. 最简实现：客户端把输入直接发给对方

先不考虑服务器。A、B 各自模拟两个角色；每人只产生“自己角色”的输入并发给对方：

```text
// 概念伪代码：P2P，输入同步，两边各跑一份相同的模拟
every tick (1/60 s):
    myInput = readKeyboardAndMouse()
    sendToPeer({tick, myInput})              // 例如 UDP，不可靠
    applyInput(localPlayer, myInput)         // 本地立刻生效，手感好
    for msg in receivedThisTick:
        applyInput(remotePlayer, msg.input)  // 收到才开始动
    simulateOneTick()
```

### 2.1 延迟：你打的是“过去的对手”

60 Hz 下每 tick 16.7 ms。设单向延迟 60 ms、RTT 约 120 ms。A 第 100 tick 看到 B 在
`x = 5.0 m`，B 实际已在 `x = 5.36 m`（6 m/s × 60 ms = 0.36 m）。**单向延迟决定画面里
对手的信息年龄；RTT 决定“本地操作被服务器确认”要等多久（一个往返），两者不是同一个量。**
角色胶囊半径 0.4 m 时，0.36 m 已足以让“看起来命中”和对方认为的命中不一致。

### 2.2 作弊：对方发来的输入不可信

B 发来的包说“这个 tick 我向前移动了 100 m”，A 没有独立事实可以反驳；B 还可以改射速、
只在自己开枪时发输入、直接改内存里的血量。**权威状态在玩家机器上，防作弊就无从谈起**。

### 2.3 状态分叉：丢一个包，两边永远对不上

输入同步假设“两边执行完全相同的输入序列”。一旦丢包或乱序：

```text
tick:        100   101   102   103
A 的输入:    +1     +1    +1    +1
B 收到:      +1    丢失    +1    +1
A 的位置:     3      4     5     6
B 的位置:     3      3     4     5   ← 从此永远差 1
```

再加两边帧率不同、浮点结果略有差异，误差会越来越大。这种“没有共享权威、只靠
对等输入”的同步叫 **lockstep（锁步）**，它要求严格确定性（第 7 节）。

最简实现暴露的是三个需求：**一个大家都信的权威、一份描述“过去某一刻”的数据、
一个让本地操作立刻生效的办法**。

## 3. 服务器权威：把“事实”放到一台机器上

第二个版本引入**服务器权威（server authority）**：客户端只上传“我想做什么”（输入），
不上传“我在哪”；服务器按固定 tick 模拟，维护唯一正确的世界状态，再广播**快照
（snapshot）**；客户端根据快照渲染其他人，本地玩家做预测（第 5 节）。

```text
// 概念伪代码：服务器权威
客户端每 tick:
    input = readInput()
    input.sequence = ++localSequence
    sendToServer(input)                  // 带序号，UDP 也可
    predictLocalPlayer(input)            // 本地先动，见第 5 节

服务器每 tick:
    for each client:
        取该客户端最早未处理的输入（按 sequence 排序）
        校验：速度/冷却/弹药/是否存活
        应用到对应角色
    模拟一 tick 的物理、战斗、AI
    每 N tick 广播一次快照（例如 20 Hz）

客户端收到快照:
    用快照更新“非本地角色”的目标状态
    用快照校正本地玩家（第 5 节）
```

服务器权威解决**事实来源**：B 说“我瞬移了”没用，服务器只执行通过校验的输入。
它也解决状态分叉：所有人最终向服务器状态收敛。代价是本地按键要等一个 RTT 才看到
角色动，手感很差——这正是插值和预测的动机。

> 服务器 tick 率是取舍：20 Hz 省带宽和 CPU，但快照间隔 50 ms、插值更“糊”；60 Hz 更跟手，
> 带宽和服务器成本约 3 倍。没有“必须 60”的规则，取决于游戏类型。

## 4. 快照、插值与外推

### 4.1 快照里有什么

典型字段：位置 3 × 4 B = 12 B（三个 `float32`），朝向 4 B（只发 yaw，或压缩到 16 位），
血量 4 B（可量化到 16 位），再加实体 id 与存活/开火等状态位。
合计约 **20 B/实体**（第 8 节带宽估算的假设）。快照还要带服务器 tick 号，
以及“已经处理到你哪个输入序号”（用于第 5 节校正）。

### 4.2 插值：故意让画面落后一点

客户端维护快照缓冲区，显示**稍微过去**的时刻：

```text
t_r = 估算的服务器当前时间 - 插值延迟 D
在缓冲区找 t0 <= t_r <= t1 的两帧
α = (t_r - t0) / (t1 - t0)          // 0 <= α <= 1
pos = pos0 + (pos1 - pos0) * α      // 逐分量线性插值
```

`D` 通常取 1~2 个快照间隔。20 Hz 快照、`D = 100 ms` 时，画面比服务器晚 100 ms，
但两个快照之间永远有数据可插，不会因“下一帧还没到”而停顿。

**数值例子**：`t0 = 1000 ms`，`t1 = 1050 ms`，`t_r = 1030 ms`，
则 `α = 30/50 = 0.6`。若 `pos0 = (0,0,0)`、`pos1 = (5,0,0)`，显示 `x = 3.0 m`
（单位米/毫秒；`α` 无量纲）。

### 4.3 外推：没数据时猜未来

如果 `t_r` 超过最新快照（`α > 1`），只能外推：

```text
pos(t) ≈ pos_last + velocity_last * (t - t_last)
```

位置误差约为 `0.5 * a * Δt²`。设 `a = 10 m/s²`：外推 100 ms 误差
`0.5 × 10 × 0.1² = 0.05 m`，通常看不出来；外推 300 ms 误差
`0.5 × 10 × 0.3² = 0.45 m`，已接近一个身位；急转弯时速度方向也错，误差更大。
外推过头再被新快照拉回，就是**橡皮筋（rubber-banding）**。

## 5. 客户端预测与服务器校正（FPS/动作游戏常用）

插值让别人的动作平滑，但本地玩家还是要等 RTT 才动，这不能接受。于是：

1. **本地立即模拟**：按下 W，本地角色马上走，同时把输入按序号存进“未确认输入”列表；
2. **服务器回包**：快照带“已处理到序号 `ack`”和该序号对应的权威状态；
3. **对账**：把本地状态设成权威状态，再把 `ack` 之后所有未确认输入重新应用一遍；
4. **平滑**：重放结果只差几厘米时，在接下来几十毫秒插值过去；差太多（被击退、
   传送、死亡）就直接以服务器为准。

```text
// 概念伪代码：预测 + 校正（不是 rollback）
onLocalTick(input):
    input.sequence = ++seq
    pending.push(input); simulateLocalPlayer(input); send(input)
onSnapshot(snapshot):
    acked = snapshot.lastProcessedInput
    localPlayer.state = snapshot.localPlayerState
    for input in pending where input.sequence > acked:
        simulateLocalPlayer(input)   // 只重放本地玩家，从权威状态往后
    drop pending where sequence <= acked
```

**数值例子**：客户端预测 `seq = 45` 时 `x = 10.00 m`。服务器回包 `ack = 42`，
算出 `x = 9.70 m`。客户端把状态设为 9.70，再重放 43、44、45 三条输入
（每条 +0.10 m），得到 `10.00 m`——和原预测相同，玩家看不到变化。
若服务器算的是 `9.65 m`，重放后是 `9.95 m`，差 5 cm，用 100 ms 平滑掉即可。

关键：**只有本地玩家被重新模拟**。其他玩家仍来自快照插值，客户端从不模拟
“别人此刻在哪”。这是它和 rollback 最直观的区别。

## 6. Rollback netcode（格斗游戏常用）

格斗游戏的约束不同：两名玩家、状态不大、双方必须看到**完全相同**的每一帧，
而且通常没有权威服务器（P2P 锁步）。做法是：

1. 每帧保存一份完整游戏状态（位置、血量、动画帧、判定框、计时器……）；
2. 本地立刻用“猜的对方输入”推进当前帧（例如猜对方继续按上次方向）；
3. 对方真实输入到达且与猜测不同时，**回到该输入对应的帧**，恢复状态，
   用真实输入重新模拟到现在；
4. 重放期间不渲染中间帧，只呈现最终结果。

```text
// 概念伪代码：rollback（与上一节的“只重放本地玩家”不同）
savedState[frame] = copyGameState()          // 每帧都存
predictedRemoteInput[frame] = lastKnownInput
onRemoteInput(frame, realInput):
    if realInput == predictedRemoteInput[frame]: return   // 猜对了
    restore(savedState[frame])                            // 回到过去
    for f from frame to currentFrame:
        applyInput(bothPlayers, f); stepSimulation()      // 重放双方输入
        savedState[f] = copyGameState()
```

**数值例子**：60 Hz 下回滚 7 帧 = `7 × 16.7 ms ≈ 117 ms`。若对方输入迟到 5 帧，
就回到 5 帧前重放 5 帧。一个格斗角色状态假设 200 个 `float`（约 800 B），
7 帧历史不到 6 KB，内存不是问题；真正的成本是**每帧重放的计算量**和
**确定性的维护成本**。

### 6.1 预测校正与 rollback 的对照

| 维度 | 客户端预测 + 服务器校正 | Rollback netcode |
|---|---|---|
| 权威在哪 | 服务器 | 通常双方锁步，没有服务器权威 |
| 本地先模拟谁 | 只模拟本地玩家 | 模拟双方角色（要立刻出画面） |
| 收到迟到信息后 | 从最新权威状态重放**未确认的本地输入** | 回到**过去某一帧**，重放双方输入到现在 |
| 需要逐帧完整状态吗 | 不需要 | 需要，每帧都要能恢复 |
| 需要确定性模拟吗 | 不要求跨机逐位一致；本机重放需可重复 | 需要跨机/逐位确定（否则重放结果不同） |
| 典型游戏 | FPS、动作、MOBA | 格斗、部分复古平台跳跃 |

两者都叫“预测”、都涉及“重放”，很容易混。判断标准：**重放的是“本地未确认输入”，
还是“过去某一帧开始的整个世界”？** 前者是预测校正，后者是 rollback。

## 7. 确定性模拟：rollback 的前提，但不等于“必须定点数”

**确定性（determinism）**：同样的初始状态 + 同样的输入序列 + 同样的 tick 步长，
在任意机器上得到逐位相同（或至少游戏逻辑相同）的结果。rollback 必须满足它，
否则“回到第 N 帧重放”会得到不同的世界。

要让模拟确定，至少要做到：固定步长（不能直接用两帧间的可变 `dt` 推进物理）；
同一 tick 的输入按玩家 id/序号排序后应用；不读墙钟、不读未初始化内存、
不依赖容器遍历顺序；随机数种子和调用顺序固定；数学库行为一致。

浮点跨平台不确定的常见来源：

| 来源 | 现象 |
|---|---|
| `a*b+c` 被编译成 FMA | 少一次舍入，结果与分开乘加不同 |
| x87 中间精度 / `-ffast-math` | 同一表达式结果不同，甚至允许重排和近似 |
| `sin/cos/sqrt` 实现不同 | 不同 CRT/CPU 的最后一位可能不同 |

工程上的应对手段：

1. **定点数/整数物理**：位置以“1/1000 米”为单位的 `int32`，所有运算可逐位复现。
   格斗游戏、锁步 RTS 常用。
2. **确定性浮点子集**：只用加减乘除、禁用 FMA/fast-math、自己实现 `sin/cos`、
   固定编译器和 CPU 架构（主机平台常见）；软浮点也可移植，但更慢。
3. **不要求跨机逐位一致**：服务器权威 + 预测校正根本不需要重放别人的世界，
   只要本地模拟和服务器足够接近，校正误差能被平滑掉。

因此：**“实现网络必须先把物理改成定点数”是错的。** 只有当你选择 rollback/锁步，
并且要求跨平台逐位一致时，定点数才成为一个现实选项；它不是唯一选项，
更不是所有网络游戏的必经步骤。FPS 通常选择“服务器权威 + 预测校正”，绕开确定性需求。

## 8. 带宽估算

固定假设（单位写清楚，否则很容易差 8 倍）：100 个实体，每个每帧快照 20 B
（12 B 位置 + 4 B 朝向 + 4 B 血量）；服务器每秒发 20 次；只算 UDP 载荷。

```text
每帧快照大小 = 100 × 20 B = 2,000 B
每秒字节数   = 2,000 B × 20 Hz = 40,000 B/s
按 1 KB = 1000 B：40,000 B/s = 40 KB/s
换算成比特   = 40,000 × 8 = 320,000 bit/s = 320 kbps
按 1 KiB = 1024 B：约 39.1 KiB/s（约 312.5 Kib/s）
```

**40,000 B/s = 40 KB/s = 320 kbps**，三个写法是同一个量，只是单位不同。
这是**每个客户端**的下行；实际还有输入、事件、语音和可靠层重传。

包头不能忽略：IPv4 头 20 B + UDP 头 8 B = 28 B/包。若 100 个实体塞进一个包，
`28 × 20 = 560 B/s`，约占载荷 1.4%；若每个实体单独发包，
`28 × 100 × 20 = 56,000 B/s`，比 40,000 B/s 的载荷还大。所以**打包本身就是优化**。

常用进一步优化：

| 手段 | 做法 | 效果（本假设下） |
|---|---|---|
| 量化 | 位置每轴 16 位（6 B），朝向 16 位（2 B），血量 16 位（2 B） | 20 B → 10 B/实体，40 KB/s → 20 KB/s（160 kbps） |
| 增量 | 只发相对上一帧变化的字段 | 静止实体几乎不占带宽，但要处理丢包后的基线 |
| 优先级/降频 | 视野内 20 Hz，视野外 5 Hz | 远处实体带宽降到 1/4 |

客户端上传的输入很小：60 Hz、每次 8 B，约 `480 B/s`，不是瓶颈。
真正的瓶颈通常不是平均带宽，而是**突发**（团战同时产生大量事件）和重传。

## 9. 小例子：一次射击从按键到命中

设服务器 20 Hz（50 ms 一帧），A 的输入到服务器 40 ms，快照回 A 40 ms，插值延迟 100 ms。

- `t = 0`：A 按下开火，本地立即播放后坐力动画；屏幕上 B 在 `x = 5.0`（100 ms 前的快照）。
- `t = 40`：服务器收到输入，在 tick 1 判定；B 实际在 `x = 5.3`，命中盒半径 0.4，
  `5.0` 与 `5.3` 都在范围内 → 命中。
- `t = 90`：快照回到 A，B 血量 -10；A 还在插值旧快照，血条未变。
- `t = 100`：A 开始显示新快照对应的时刻，B 的血条约 100 ms 后掉。

如果 B 在这 50 ms 内已躲到掩体后（服务器看到 `x = 6.0`），而 A 屏幕上仍是
`x = 5.0`，服务器就判“未命中”——这就是“我明明打中了却没掉血”。
解决它需要**延迟补偿**：服务器按 A 的报告，把 B 的碰撞体倒回 A 看到的时间点
再做射线检测。这是服务器端判定技巧，和客户端预测/插值是两条线。

## 10. 本工程的实现（已落地）

网络层不在 2D 幸存者里，而是引擎级模块 `engine/src/net/`：

1. **传输层**：[NetTransport.h](../../../engine/src/net/NetTransport.h) 用 vendored
   [ENet 1.3.18](../../../third_party/enet) 封装 UDP 可靠/有序/无序通道、ACK、重传、分片与 RTT；
   当前输入和快照都走可靠有序通道，先保证正确性。
2. **快照序列化**：[NetReplication.h](../../../engine/src/net/NetReplication.h) 给动态实体分配
   `NetworkIdentity`，按反射字段做增量快照；首帧/重连发全量，之后只发变化字段和 Transform。
3. **客户端时钟与插值**：`ReplicationClient` 估计服务端时间，保存最近样本，
   在“服务端时间 − 100ms”处插值；超出最新快照时最多外推 250ms。
4. **本地预测 + 校正**：`NetRuntime` 只对客户端自己的实体调用玩法提供的 `predictLocal`；
   快照位置误差超过 1.5m 时直接拉回。当前**没有**保存未确认输入并重放，属于轻量预测校正。
5. **延迟补偿与 rollback**：暂未实现。射击命中以服务端当前时间为准，高速移动目标会有
   “看起来命中但没掉血”的情况；只有格斗/锁步类才需要逐帧状态和 rollback。
6. **接入方式**：[NetRuntime.h](../../../engine/src/net/NetRuntime.h) 的 `NetGameHooks`
   把“哪些对象同步、输入怎么驱动玩家、客户端怎么进入副本模式”留给玩法；2D/3D 幸存者
   共用同一套实现，接入步骤见 [网络同步](../../版本文档/网络同步.md)。

## 11. 实验与观察

现在可以实际运行：`ErMao.exe --net-test --noeditor` 做进程内回环自检；
两台机器用 `--net-host` / `--net-join` 手动联机。下面是观察清单：

| 操作（实现后） | 预期观察 | 对应原理 |
|---|---|---|
| 上行/下行各加 100 ms 延迟 | 本地移动仍立刻响应；其他角色平滑但滞后 | 预测 + 插值 |
| 让 2% 的输入包丢失 | 不应出现永久分叉；预测被服务器校正 | 权威状态 + 重放 |
| 把插值延迟调到 0 / 外推调到 500 ms | 前者在快照边界抖动，后者急转弯时“弹回” | `α` 越界；外推误差增长 |

排查入口：先确认“本地玩家是否预测”，再确认“快照时间戳是否单调”，
最后确认“重放时输入顺序和随机数种子是否一致”。大多数“网络手感差”不是带宽问题，
而是时间戳/插值延迟/校正平滑三者没对齐。

## 12. 自测题（含答案）

1. **客户端预测校正和 rollback 最关键的区别是什么？**
   前者从最新权威状态重放“本地未确认输入”，只模拟本地玩家；后者回到过去某一帧，
   重放双方输入和整个世界，需要逐帧状态与确定性。见 6.1。

2. **“要做网络，必须先把物理改成定点数”这句话对吗？**
   不对。服务器权威 + 预测校正**不要求跨机逐位一致**（但同一客户端重放自己的输入
   仍需可重复）；只有 rollback/锁步且需要跨平台一致时，定点数才是常见手段之一，
   不是唯一手段。见第 7 节。

3. **100 个实体、每实体 20 B、20 Hz，带宽是多少？**
   `100 × 20 × 20 = 40,000 B/s = 40 KB/s = 320 kbps`（1 KB = 1000 B）。
   位置量化到每轴 16 位后实体约 10 B，降到 20 KB/s = 160 kbps。见第 8 节。

4. **外推 300 ms、加速度 10 m/s²，位置误差约多少？**
   `0.5 × 10 × 0.3² = 0.45 m`（见 4.3）；急转弯时速度方向也错，误差更大。

5. **为什么 P2P 输入同步防不了作弊？**
   权威状态在玩家机器上，对方无法验证你发来的输入是否合法（见 2.2）。
