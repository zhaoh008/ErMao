## 1. 现象：Inspector 为什么"什么都能显示"

选中一个物体，检视器里出现：

```text
变换 (Transform)：位置 [x][y][z] / 旋转 [yaw][pitch][roll] / 缩放 [x][y][z]
Mesh Renderer：网格 [cube ▾] / 基础色 [颜色块] / 粗糙度 [====|----] 0.500
              金属度 [|--------] 0.000 / ...
```

这些控件不是为 `MeshRenderer` 手写的：换成 `Rigid Body`、`Point Light`、`Enemy`，检视器也能自动列出字段并生成合适的控件。另一半是存档：改一个物体的 `roughness`，保存场景，再用编辑器重新打开它，数值必须**还是那个数**——不是 0.499999，也不是 0.500001。UI 与存档这两件事，本工程用**同一份字段描述**驱动。

## 2. 最简实现：每个组件手写 Save/Load

**概念伪代码**（不是本仓库代码）：

```cpp
struct MeshRenderer { std::string mesh; Vec4 albedo; float roughness, metallic; };

void DrawMeshRenderer(MeshRenderer& m) {
    ImGui::InputText("mesh", ...);
    ImGui::ColorEdit4("albedo", &m.albedo.x);
    ImGui::DragFloat("roughness", &m.roughness, 0.01f, 0.04f, 1.0f);
    ImGui::DragFloat("metallic", &m.metallic, 0.01f, 0.0f, 1.0f);
}
void SaveMeshRenderer(const MeshRenderer& m, JsonValue& out) {
    out.Set("mesh", JsonValue(m.mesh));
    out.Set("albedo", Vec4ToJson(m.albedo));
    out.Set("roughness", JsonValue(m.roughness));
    out.Set("metallic", JsonValue(m.metallic));
}
void LoadMeshRenderer(MeshRenderer& m, const JsonValue& in) {
    m.mesh = in["mesh"].AsString(m.mesh);
    m.albedo = JsonToVec4(in["albedo"], m.albedo);
    m.roughness = in["roughness"].AsFloat(m.roughness);
    m.metallic = in["metallic"].AsFloat(m.metallic);
}
```

一个组件这样写没问题。问题在组件数量变成 20 个之后。

## 3. 它具体在哪里坏掉

**加一个字段要改三处。** 给 `MeshRenderer` 加 `emissive`：结构体加成员、`DrawMeshRenderer` 加一行控件、`Save/Load` 各加一行。漏掉存档那一行，编辑器里能调、保存后丢失；漏掉 UI 那一行，字段存在但用户看不见。

**类型靠人记，错了不报错。** 上例里 `Vec4` 要自己写 `Vec4ToJson`，`std::string`、`bool`、`int`、`Vec3` 各一套。如果某天把 `roughness` 的类型从 `float` 改成 `Vec2`，编译器不会提醒你 `SaveMeshRenderer` 还在按 float 读。

**UI 与存档是两套重复的字段清单。** 两边的顺序、默认值、范围、显示名各自维护；改了一边忘另一边，就会出现"检视器显示 0.5，存档里是 0.3"。

**读档需要"凭空造组件"。** JSON 里只写了 `"type": "Mesh Renderer"`，读的时候要能根据名字创建对应组件。手写方案里通常是一长串 `if (type == "Mesh Renderer") AddComponent<MeshRenderer>()`，加组件就要加分支。

**字段改名直接破坏旧存档。** 把 `"roughness"` 改成 `"rough"`，旧文件里的 `roughness` 没人读，新字段用默认值；没有版本号、没有迁移函数，只能靠人记得。

## 4. 正式方案：字段描述 + 工厂 + JSON

### 4.1 字段描述（`FieldDesc`）

每个字段登记四类信息：**名字**（JSON key）、**显示名**（UI label）、**类型**（决定控件和读写方式）、**怎样从对象指针拿到字段地址**。下面是**源码节选**（为排版把 `name`/`label` 两行合并）：

```cpp
enum class FieldType { Bool, Int, Float, Vec2, Vec3, Vec4, Color, String, MeshAsset, TextureAsset };
struct FieldDesc {
    std::string name, label;             // JSON key / UI 显示名
    FieldType   type = FieldType::Float;
    std::function<void*(void*)> access;  // 从组件指针取字段地址
    float       min = 0.0f, max = 1.0f;
    bool        hidden = false;
};
```

注意 `access` 是 `std::function<void*(void*)>`，**不是** `void* member`。它由成员指针生成，既避开 `offsetof` 对非标准布局类型的限制，也把"哪个类的哪个成员"编码进类型系统（**源码节选**，变量名缩短）：

```cpp
template <typename C, typename T>
FieldDesc& Field(const char* key, FieldType type, T C::*member, const char* label = nullptr,
                 float min = 0.0f, float max = 1.0f) {
    FieldDesc d; d.name = key; d.label = label ? label : key;
    d.type = type; d.min = min; d.max = max;
    d.access = [member](void* o) { return &(static_cast<C*>(o)->*member); };
    fields.push_back(std::move(d));
    return fields.back();
}
```

每个组件实现一次 `Describe`（**源码节选**，省略其余字段）：

```cpp
void MeshRenderer::Describe(TypeInfo& t) {
    t.factory = [](GameObject* go) -> Component* { return go->AddComponent<MeshRenderer>(); };
    t.Field("mesh", FieldType::MeshAsset, &MeshRenderer::mesh, "网格");
    t.Field("albedo", FieldType::Color, &MeshRenderer::albedo, "基础色");
    t.Field("roughness", FieldType::Float, &MeshRenderer::roughness, "粗糙度", 0.04f, 1.0f);
    ...
}
```

`ER_COMPONENT(Class, "Name")` 宏声明 `Describe` 与 `GetTypeInfo()`；`GetTypeInfo()` 调 `Reflection::Register<Class>(...)`，用函数内 `static` 保证"类型信息 + Describe 只执行一次"，并把 `TypeInfo*` 推入全局表。

### 4.2 反射驱动的检视器（**源码节选**，省略 `PushID`/`PopID`）

```cpp
for (const auto& field : info.fields) {
    if (field.hidden) continue;
    void* value = field.access(component.get());
    DrawField(field, value, assets);       // 按 field.type 选控件
}
```

`DrawField` 是一个 `switch`：`Bool → Checkbox`、`Int → DragInt`（`shape` 特判成下拉框）、`Float → DragFloat`、`Vec3 → DragFloat3`、`Vec4/Color → ColorEdit4`、`String → InputText`、`MeshAsset/TextureAsset → 下拉框`。新增字段只需在 `Describe` 里加一行，UI 与存档同时生效——但**不是所有类型都有控件**：`Vec2` 在 `DrawField` 里是空分支，`SpriteRenderer` 的 `size`/`offset` 能存能读，检视器里却不显示。

### 4.3 JSON 值

`core/Json.h` 是手写的最小 JSON：对象/数组/数字/字符串/布尔/null，支持 `//` 注释（方便手改）。内部数字统一存 `double`：

- **解析**：`ParseNumber` 用 `strtof` 得到 `float` 再拓宽到 `double`。理由写在注释里：场景数值都是 `float`，`strtod` + 窄化可能差 1 ULP；`strtof` 正确舍入到 float。
- **输出**：`NumberToString` 先判断"整数值"（`v == (long long)v` 且 `|v| < 1e15`），是就按 `%lld` 打印（所以 `1.0f` 在文件里是 `1`）；否则用 C++17 `std::to_chars` 打**最短可往返表示**：如果 `double(float(v)) == v`，按 `float` 打；否则按 `double` 打。`to_chars` 失败才退回 `%.9g`。

"最短可往返"的意思是：文本 → 同类型 → 文本 完全一致，且没有 `0.30000000000000004` 这种噪音。代价是**只对 float 精确**；如果以后加 `double` 字段，`SerializeField` 仍按 float 走，会丢精度。

### 4.4 场景往返（`World::ToJson` / `FromJson`）

`ToJson` 的结构（`Dump(2)` 会展开成多行，这里压成示意）：

```json
{
  "version": 1,
  "levelKind": "demo",
  "sun": { "direction": [..], "color": [..], "intensity": 3.2, "ambientUp": [..], ... },
  "objects": [
    {
      "id": 3, "name": "木箱_A", "active": true, "parent": 0,
      "position": [-12, 0.5, 2], "rotation": [0, 0, 0, 1], "scale": [1, 1, 1],
      "components": [
        { "type": "Mesh Renderer", "mesh": "cube", "albedo": [0.55, 0.36, 0.22, 1],
          "roughness": 0.7, "metallic": 0, "emissive": 0, "uvScale": 1,
          "texture": "noise", "castShadow": true }
      ]
    }
  ]
}
```

几个必须知道的事实：

- `version` 写了 `1`，但 `FromJson` **从不读它**——没有迁移机制；
- 物体的 `id/name/active/parent/position/rotation/scale` 是**手写**的，不走反射；只有组件的字段走 `FieldDesc`；
- 组件按 `object->Components()` 的插入顺序写，字段按 `Describe` 的注册顺序写，所以同一场景两次保存的文本顺序稳定（可 diff）；
- `hidden == true` 的字段既不进 JSON 也不进检视器；但当前仓库**没有任何地方把 `hidden` 设为 true**，它只是个预留钩子。

`FromJson` 的流程：

1. 校验根是对象且含 `objects`，否则报错返回；
2. `Clear()` 清空世界（所有 `GameObject*` 失效）；
3. 读 `levelKind` 和可选的 `sun`；
4. **第一遍**：逐个对象创建、设变换、恢复 `id`（保留存档 id，保证父子引用稳定）、记录 `parent`、按 `"type"` 查 `Reflection::Find`，用 `factory` 造组件，再逐字段 `DeserializeField`；
5. **第二遍**：按记录恢复父子关系；
6. `m_started = true`，`RebuildNavigation()`（AI 栅格要跟着场景重建），打印对象数。

容错行为：

| 情况 | 行为 |
|---|---|
| 未知组件类型 | `LogWarn("场景引用了未知组件类型: ...")`，跳过该组件 |
| 已知类型但没设 `factory` | `AddComponentByTypeName` 返回 null，静默跳过 |
| JSON 里缺某个字段 | 保留组件构造时的默认值（不报错） |
| JSON 里有额外字段 | 忽略 |
| 字段名改了 | 旧 key 被忽略，新字段用默认值；无迁移 |
| 数组长度不够（如 `Vec3` 只有 2 个） | `JsonToVec3` 返回当前值，不写坏内存 |

### 4.5 PIE 快照（**源码节选**，省略 `error` 声明与日志）

```cpp
void Editor::EnterPlayMode(World& world) {
    m_snapshot = world.ToJson().Dump();
    Play();
}
void Editor::ExitPlayMode(World& world) {
    Stop();
    if (!m_snapshot.empty()) {
        JsonValue root = JsonValue::Parse(m_snapshot, &error);
        if (error.empty()) world.FromJson(root);   // 内部会 Clear
    }
    Select(nullptr);
}
```

快照是**整个场景的 JSON**，比"记录每个物体的增量"简单可靠；回滚 = `Clear + FromJson`，所有对象指针失效。所以：

- `Editor::Draw` 每帧检查 `m_selected` 是否还属于当前世界（`IsPendingDestroy` 或 `FindById(m_selectedId) != m_selected`），失效就清空；
- 玩法代码不能长期缓存 `GameObject*`，要按名字/ID 重查。修复记录 P2-20 就是删掉了 `Engine::m_player` 这个跨 PIE 的裸指针；
- 快照字符串在 `ExitPlayMode` 后**不清空**，下次 `EnterPlayMode` 覆盖；所以在非播放状态读它没有意义。

## 5. 范围与边界（不要声称"所有组件都支持"）

注册表由 `World::Init` 与 `Engine::Init` 汇总，共 **27 种预注册组件**：

- `RegisterAllComponents()`：`Mesh Renderer`、`Camera`、`Directional Light`、`Point Light`、`Rigid Body`、`Spinner`、`Sprite Renderer`、`Sprite Animator`；
- `RegisterAgentComponents()`：`Nav Agent`、`Player Controller`；
- `World::Init` 里追加：`Animator`、`Third Person Controller`、`Health`、`Combat`、`Projectile`、`Enemy`、`Skinned Character`、`Particle Emitter`；
- `Engine::Init` 在 `m_world.Init()` 之后调用游戏模块的 `RegisterSurvivorsComponents()` / `RegisterSurvivors3DComponents()`：`Survivors Player`、`Survivors Enemy`、`Survivors Projectile`、`Survivors Gem`、`Survivors3D Player`、`Survivors3D Enemy`、`Survivors3D Projectile`、`Survivors3D Gem`、`Survivors3D Effect`。这样 `--script` 和 `scene.load` 开始前注册表已完整。

`ER_COMPONENT` 的 `GetTypeInfo()` 仍会在第一次被调用时**惰性注册**：如果新增组件只写了 `Describe` 而没有加入上述预注册清单，它只有在本进程中被 `GetTypeInfo()` 碰过才存在于注册表；换一次启动直接读含该组件的场景时，`Reflection::Find` 会找不到类型，`FromJson` 打印"未知组件类型"并跳过。因此新增 `ER_COMPONENT` 类型时必须同步预注册。

`Reflection::Find` 是精确字符串比较（区分大小写与空格），组件名必须与注册时的显示名完全一致。

其他不覆盖的东西：

- 组件基类的 `enabled` **不参与序列化**，读档后都是默认 `true`；物理运行时状态（`sleepTimer`、`grounded`）不是字段，不存；
- `NavAgentComponent::state` 是运行时状态，却被注册成 `Int` 字段：会存档、能在检视器里改，但下一帧就被感知重算覆盖——这是"把运行时状态混进反射"的反例；
- `min/max` 只用于检视器控件，**读档不 clamp**（见 §6.4）。

## 6. 数值例子：两个"看起来一样、字节不一样"的坑

### 6.1 浮点：`0.7071068f` 与 `%.6g`

设 `MeshRenderer::roughness = 0.7071068f`（45° 的余弦近似，合法范围 `[0.04, 1]`）。

- `std::to_chars` 的最短 float 表示：`0.7071068`；再用 `strtof` 读回，得到**同一个** float。
- 旧做法 `%.6g`：输出 `0.707107`（6 位有效数字）；`strtof("0.707107")` 得到 `0.7071070075035095`，比原值高 **3 个 ULP**。

所以：

```text
第一次保存： "roughness": 0.7071068
用 %.6g 读入再保存： "roughness": 0.707107    ← 字节不一致
再读再存： "roughness": 0.707107              ← 之后稳定
```

这也说明"`%.6g` 一定只差 1 ULP、一定从第 4 位丢精度"是错的：`3.2f` 用 `%.6g` 输出 `3.2` 可以无损；`0.7071068f` 差 3 ULP；`0.38268343f` 用 `%.6g` 会差到 14 ULP。**丢不丢精度取决于这个 float 的最短表示需要几位十进制**。

### 6.2 四元数：30° yaw 的一次归一化

`Quat::FromEuler(30°, 0, 0)` 得到的 float 四元数是 `q = (0, 0.25881904, 0, 0.9659258)`，float 长度是 `0.99999994`，与 1 差 `-5.96e-8`。`GameObject::SetRotation` 的策略是（**源码节选**）：

```cpp
const float length = std::sqrt(q.x*q.x + q.y*q.y + q.z*q.z + q.w*q.w);
m_rotation = (std::fabs(length - 1.0f) > 1e-4f) ? q.Normalized() : q;
```

`5.96e-8 < 1e-4`，所以**保持原样**，下次保存还是 `rotation: [0, 0.25881904, 0, 0.9659258]`。如果恢复成"每次都 `Normalized()`"，它会算 `inv = 1/l` 再逐分量乘，得到 `q' = (0, 0.25881907, 0, 0.96592593)`：`y` 大 **1 ULP**、`w` 大 **2 ULP**，下一次 `Dump` 就写出不同的文本；再加载再归一化才稳定。**这就是"加载→保存"文件变化的来源**——不是 JSON 格式，而是"对已经接近单位长度的四元数再做一次归一化"的舍入。

阈值 1e-4 的含义：误差小于它视为"已经是单位四元数"，保留原始位；大于它（手改过的、累计误差大的）才归一化。阈值不能取 0（浮点误差永远非零），也不能太大（会容忍真正非单位的旋转）。

### 6.3 自检在检查什么

```bat
build\bin\ErMao.exe --test-serialize --frames 2
```

`Engine` 的逻辑（**源码节选**，简化：`reload` 是原代码里的 lambda，日志参数省略）：

```cpp
const std::string original = m_world.ToJson().Dump();
const std::string first  = reload(original);   // Clear + Parse + FromJson + ToJson
const std::string second = reload(first);
const bool stable    = (first == second);
const bool identical = (original == first);
LogInfo("[自检] 序列化往返: %zu -> %zu 个对象，再次往返稳定=%s，首次字节一致=%s", ...);
```

- `stable`：第二次往返与第一次完全一致，说明序列化是**幂等**的（没有"每次加载都改变一点"的隐藏状态）；
- `identical`：第一次就一致，说明连一次性的归一化漂移都没有；
- 不一致时只打印 120 字符的差异片段，**不会让程序失败或返回错误码**；它是一份日志，不是断言。对象数取决于关卡（默认 `survivors`，可用 `--level` 指定），不要照抄历史示例里的具体数字。

### 6.4 一个容易写错的实验

常见误解是"把文件里某个 `roughness` 改成 2.0 → 加载 → 检视器显示被 clamp 到 1.0（`Field` 的 min/max 生效）"。**实际不是**：

- `DeserializeField` 对 `Float` 只做 `value.AsFloat(当前值)`，没有任何 clamp；
- 所以加载后字段就是 `2.0`，检视器也显示 `2.0`；
- `ImGui::DragFloat(label, value, 0.01f, min, max)` 的边界只在**用户拖动控件**时夹紧；而且没有 `ImGuiSliderFlags_AlwaysClamp` 时，Ctrl+点击手动输入可以越界；
- 正确的实验是：改成 2.0 → 加载后显示 2.0 → 拖动一下这个控件，才会被夹回 `[0.04, 1]`。

## 7. 进阶与工程取舍

**为什么用成员指针而不是偏移量。** `offsetof` 对非标准布局类型是条件支持的；成员指针 `T C::*` 由编译器保证正确，还能在 `Field` 模板里推导出所属类 `C`，避免"把 A 类的字段注册到 B 类"这种错误。运行时仍然只有 `void*` + `switch(type)`，类型安全靠"注册时写对"——写错不会报错，只会读到错误的字节。

**确定性来自哪里。** `JsonValue` 的对象成员是 `vector<pair<string, JsonValue>>`，保留插入顺序（不是 `map` 的字典序）；`World::ToJson` 按层级前序遍历、组件按插入顺序、字段按 `Describe` 顺序。三者固定，文本就可复现、可 diff。反过来说，调整 `Describe` 里两行的顺序就会让所有旧场景的文本顺序变化（语义不变，但 diff 很大）。

**ID 与父子。** `FromJson` 保留存档里的 `id`，并把 `m_nextId` 推到 `max(id)+1`；父子关系第二遍才恢复，避免"父还没创建"。这也意味着**同一个 id 在 JSON 里出现两次**时，后一个会覆盖 `m_idToObject` 的映射，行为未定义——没有查重。

**为什么不做增量快照。** PIE 只需要"进入时存、退出时回滚"，整场景 JSON 几十 KB，实现和调试都简单；增量需要监听每个字段的修改、处理对象增删和父子变化，复杂度高一个量级。代价是回滚会重建所有对象，指针全失效。

**尚未实现但迟早要做的：** 版本迁移（`version` 已写入，读的时候要按版本分支、补默认值/改名）；字段重命名兼容（旧 key 别名表）；资产引用（现在 `mesh`/`texture` 存名字字符串，重命名资产不会更新场景，工业做法是 GUID/路径 + 资产数据库）；二进制/压缩格式（文本适合 diff，不适合大场景加载速度）。
