## 1. 要解决的问题

一帧里要做的事按顺序是：

```
收消息 → 采样输入 → 推进时间 → 固定步长仿真(物理/AI/角色) → 渲染(场景→RT→后处理) → UI → Present
```

看起来是流水账，但有两个真正需要数学的地方：

```
   ┌─────────────────────────────────────────────────────────────┐
   │ while (running)                                             │
   │   1. 收消息 + 采样输入   (Input::BeginFrame → Poll)          │
   │   2. 推进时间            (Timer::Tick, dt = min(dt, 0.1))    │
   │   3. 固定步长仿真        (while acc >= h) FixedUpdate(h)     │
   │   4. 可变步长更新        (Update(dt): 相机/动画/UI)           │
   │   5. 渲染                (Shadow→Sky→Opaque→Post)            │
   │   6. Present             (EndFrame: 等 vsync)                │
   └─────────────────────────────────────────────────────────────┘
```

1. **时间推进**：`dt` 取多大？掉帧了怎么办？
2. **固定步长与可变步长的关系**：为什么物理用固定步长、渲染用可变步长，两者怎么衔接？

## 2. 数学：时间积分与步长

### 2.1 显式欧拉的稳定性

设一个一阶系统 `ẋ = -kx`（例如阻尼、弹簧），显式欧拉：

```
x_{n+1} = x_n + h * (-k x_n) = (1 - kh) x_n
```

要让它不发散，必须 `|1 - kh| < 1`，即

```
0 < h < 2/k        （k 是系统刚度）
```

- 刚度 `k` 越大（例如硬弹簧、快速衰减），允许的 `h` 越小；
- 如果 `h` 随帧率变化（30fps 时 h=33ms，144fps 时 h=7ms），同一套参数在不同机器上表现不同 → **物理必须用固定步长**。

### 2.2 固定步长的累加器

```cpp
m_accumulator += dt;                  // 这一帧实际过去了 dt
int steps = 0;
while (m_accumulator >= kFixedDt && steps < kMaxSubSteps) {
    m_world.FixedUpdate(kFixedDt);    // 物理/AI/角色位移
    m_accumulator -= kFixedDt;
    ++steps;
}
if (steps == kMaxSubSteps) m_accumulator = 0;   // 防死亡螺旋
m_world.Update(dt);                   // 视觉相关（相机跟随、动画时间）
```

**误差分析**：真实经过时间 `dt`，实际仿真时间 `steps * h`，剩余 `r = dt - steps*h ∈ [0, h)`。
- 每帧丢下的 `r` 会在下一帧补上，长期平均仿真时间 = 真实时间（无系统性漂移）；
- 但**相位**最多滞后 `h`（这里 1/60 ≈ 16.7ms），这是固定步长无法避免的。

**死亡螺旋**：如果一帧耗时 200ms，按 16.7ms 步长要补 12 步，补完更慢 → 下一帧更慢。
所以必须有 `kMaxSubSteps`（本工程取 5）并在触顶时**丢弃积压时间**——宁可游戏变慢，也不能卡死。

### 2.3 为什么渲染不插值

固定步长与渲染帧率的比值不是整数时，理论上应该在两个物理状态之间插值再渲染（`α = accumulator / h`）。
本工程没有做，原因：

- 角色相机是**每帧**从当前位置跟随的（见第 15 讲），插值收益被相机平滑吃掉；
- 教学优先：多一层插值会让"为什么位置是这个值"更难对照。

这是已知取舍，写进 `文档/版本文档/修复记录.md` 的取舍清单。

## 3. 代码

### 3.1 主循环骨架（`Engine::MainLoop`）

```cpp
while (m_running) {
    Input::BeginFrame();              // 1) 清边沿，再收消息（顺序不能反，见第 13 讲）
    if (!m_window.Poll()) break;
    Input::SetMouseState(...);
    Timer::Tick();

    const float dt = std::min(Timer::Delta(), 0.1f);   // 2) 夹住 dt，防止断点后瞬移
    ...
    UpdateGameplay(dt);               // 3) 固定步长仿真
    ...                               // 4) 相机、UI、渲染
    m_device.EndFrame(m_vsync);       // 5) Present
}
```

`std::min(dt, 0.1f)` 的作用：调试器断点、窗口拖动会带来几百毫秒的 `dt`，
夹到 100ms 后，最多补 5 步（5×16.7≈83ms），不会一帧算几百步。

### 3.2 计时器（`Timer::Tick`）

```cpp
double now = Now();           // QueryPerformanceCounter
m_delta = float(now - m_last);
m_last = now;
```

用 `double` 存绝对时间：`float` 在 10 万秒后精度只剩 ~10ms，长时间运行会抖。

### 3.3 分层初始化顺序

```
Log → Timer → JobSystem → CoInitialize → Window → Device → Renderer → Assets → World → ImGui → Editor
```

释放顺序完全相反（`Engine::Shutdown`）。原因：`Renderer` 在 `Device` 之上、`Editor` 依赖 `ImGui`，
任何"上层先死、下层还用"都会立刻崩。

## 4. 实验

```bat
:: 1) 跑 300 帧，打印最终统计
build\bin\ErMao.exe --demo --frames 300

:: 2) 观察固定步长：日志里玩家位置每 30 帧记录一次
build\bin\ErMao.exe --smoke --frames 200 --level thirdperson
:: [冒烟] 帧 30 玩家位置 (0.00, 0.95, 12.50)
:: [冒烟] 帧 120 玩家位置 (0.00, 0.95, 5.59)
```

按 5 m/s 走 90 帧（1.5s）应该走 7.5m；实际 12.50→5.59 走了 6.91m，
差值是前 30 帧的起跑加速与台阶碰撞造成的——说明**位移确实由固定步长积分**，不是按帧数硬编码。

## 5. 常见错误

| 错误 | 后果 | 本工程怎么避免 |
|---|---|---|
| `dt` 不夹上限 | 断点后一帧瞬移/穿透 | `min(dt, 0.1f)` + 最多 5 步 |
| 物理用可变步长 | 不同帧率下手感/稳定性不同 | 固定 1/60 |
| 累加器不清零 | 卡顿后永久积压（死亡螺旋） | 触顶丢弃 |
| 用 `float` 记绝对时间 | 长时间运行精度丢失 | `double` |

## 练习（故意改坏）

1. 把 `kMaxSubSteps` 从 5 改成 50：**预期**卡顿后仍能追上，但一帧可能算 50 步（更卡），观察 FPS 面板的帧时间曲线。
2. 把 `std::min(Timer::Delta(), 0.1f)` 的 0.1 改成 1.0：**预期**在断点/拖动窗口后角色瞬移，甚至穿过墙。
3. 把 `while` 改成 `if`：**预期**在低帧率下游戏变慢（仿真时间 < 真实时间），但画面不卡。
