> 这一讲只回答一个问题：**一帧到底该在什么时候、用多大的步子更新游戏世界？**
> 实现状态：**已实现** = 主循环、`Timer`、固定步长 + 累加器、子步上限与 `dt` 裁剪；

## 0. 本讲地图

| 你会看到 | 内容 |
|---|---|
| 一个现象 | 按住 W，角色持续向前走；松开就停 |
| 你的理解 | `while (running) { 处理输入; 更新世界; 渲染; }` —— 这个理解是对的 |
| 它缺什么 | “更新世界”需要知道**过了多少时间**，而这个时间不能直接用两帧的间隔 |
| 最简单实现 | `dt = now - last; pos += vel * dt;` |
| 它怎样坏 | 卡顿、穿墙、弹簧爆炸、同一操作在不同机器上结果不同 |
| 正式方案 | 固定步长 + 累加器：真实时间照常流逝，仿真只按 `1/60 s` 一步步走 |
| 源码落点 | `Engine::MainLoop`、`Engine::UpdateGameplay`、`Timer::Tick` |

## 1. 先看现象：按住 W 为什么能一直走

你在 UE 里做过角色移动：按 W，角色沿相机前方走；松开，速度降为零。到了自己写引擎，最自然的想法就是：

```cpp
// 概念伪代码：最朴素的“每帧更新一次”
while (m_running) {
    处理输入();       // W 现在是否按住？
    更新游戏世界();   // 角色位置 += 速度 * ???
    渲染画面();
}
```

这个结构**没有错**，它已经包含了引擎最核心的三件事：输入、仿真、渲染。缺的只有一样东西：

> `更新游戏世界()` 怎么知道“从上一帧到现在过了多久”？

如果每帧固定把位置加 `0.1` 米，那么 60 FPS 的机器一秒走 6 米，144 FPS 的机器一秒走 14.4 米。所以必须把**真实经过的时间**传进去。于是有了第二版：

```cpp
// 概念伪代码：用两帧的时间差推进
double now = Now();
float  dt  = float(now - last);
last = now;

处理输入();
更新游戏世界(dt);   // pos += velocity * dt
渲染画面();
```

到这里，你的理解和“引擎主循环”的差距已经很小了。真正的难点不是 `while`，而是 **`dt` 本身不可靠**：它会忽大忽小，会因卡顿变成几百毫秒，而游戏世界里的某些计算对步长非常敏感。这一讲剩下的部分，就是从“为什么 `dt` 不能直接拿来做所有更新”开始，一步步走到 `Engine::UpdateGameplay` 的真实实现。

## 2. 最简单、能工作的实现

先只考虑一个角色和一面墙，把世界简化成几个数：

```cpp
// 概念伪代码：一个会走、会撞墙的角色
struct Player {
    Vec3  position{0, 0, 0};
    Vec3  velocity{0, 0, 0};
    float radius = 0.4f;
};

Player player;
const float speed = 5.0f;   // m/s

void UpdateWorld(float dt) {
    Vec3 wish = ReadMoveInput();          // 键盘方向，长度 0 或 1
    player.velocity = wish * speed;

    Vec3 next = player.position + player.velocity * dt;
    if (!IntersectsWall(next, player.radius)) {
        player.position = next;           // 没撞墙才移动
    }
}
```

这段代码已经能跑：按 W 一直走，撞墙停住。它也是理解后面所有机制的基础。下面用具体数字让它坏掉。

**具体场景**：角色以 `5 m/s` 朝墙走，墙厚 `0.1 m`，角色半径 `0.4 m`。

- 60 FPS：`dt = 0.0167 s`，每帧走 `0.083 m`，小于半径，`IntersectsWall` 能在角色中心进入墙之前发现碰撞。
- 30 FPS：`dt = 0.0333 s`，每帧走 `0.167 m`，仍然小于半径，能发现。
- 卡顿一次 200 ms：`dt = 0.2 s`，这一帧走 `1.0 m`。角色中心从墙前 `0.45 m` 直接跳到墙后 `0.55 m`，`IntersectsWall` 只看“下一帧的位置”，于是**整面墙被穿过去**。

玩家看到的现象：拖动窗口、切出去再切回来、加载资源卡一下，角色就“闪”到了墙另一边。这不是碰撞代码写错了，而是**一次更新的步子太大，采样点跨过了障碍物**。

## 3. 简单实现还会在哪里坏

### 3.1 弹簧与阻尼：`dt` 一大就发散

先看一个一阶系统，例如“速度按比例衰减”：

```
v' = -k v
v_{n+1} = v_n + h(-k v_n) = (1 - k h) v_n
```

要让 `v` 收敛而不是越变越大，需要 `|1 - k h| < 1`，即 `h < 2/k`。取 `k = 100`，要求 `h < 0.02 s`；30 FPS 的 `h = 0.033` 就会让速度正负翻转并放大。

再看弹簧（相机臂、布料、受击回弹），它是二阶系统：

```
x' = v
v' = -k x          // ω = sqrt(k)
```

最直观的显式欧拉（速度和位置都用旧值）离散矩阵的特征根满足 `|λ|² = 1 + k h²`，**只要 `h > 0` 振幅就会缓慢增长**；步长越大，增长越快。换成本工程物理使用的半隐式欧拉（先更新速度，再用新速度更新位置）：

```
v = v + (-k x) * h
x = x + v * h
```

它在一定范围内保持振幅不放大，条件是

```
h < 2 / ω = 2 / sqrt(k)
```

取 `k = 400`（`ω = 20 rad/s`），要求 `h < 0.1 s`；60 Hz 的 `h = 1/60` 满足条件。但如果弹簧更硬，`k = 40000`（`ω = 200`），就要求 `h < 0.01 s`，60 Hz 不再够——**固定步长只保证每台机器用同一个 `h`，不保证这个 `h` 对你的刚度足够小**。

不必现在背下所有稳定域。先记住结论：**步长越大，越容易把“应该衰减的振动”算成“越振越大”**。表现到画面上，就是相机臂抖动、角色受击后原地高频颤、布料炸开。换一台帧率更低的机器，同一个 `k` 可能就炸；这就是“物理参数在不同机器上手感不同”的来源之一。

### 3.2 同一段输入，两台机器结果不同

假设你录制了一段 1 秒的输入做回放：前 0.5 秒按 W，后 0.5 秒松开。A 机器稳定 60 FPS，B 机器在 30~90 FPS 之间波动。因为每帧的 `dt` 不同，碰撞检测发生的时刻不同，角色可能在 A 上停在墙前，在 B 上穿墙。**回放/网络同步/自动化测试都要求“同样的输入序列产生同样的状态序列”**，而“每帧更新一次”的步长由机器决定，做不到这一点。

### 3.3 一次卡顿会把积压全部倒进这一帧

如果 200 ms 没有出帧，下一帧直接用 `dt = 0.2`，所有系统都会收到一个巨大的步长：动画跳帧、粒子瞬移、AI 寻路一步跨过格子。更糟的是，如果你为了“追上时间”在一帧里连续更新很多次，这一帧会算得更久，下一帧的 `dt` 更大，形成**死亡螺旋**。

## 4. 正式方案：把“真实时间”和“仿真步长”分开

### 4.1 一句话原理

> 真实时间照常流逝；游戏世界的仿真只用**固定长度** `h` 的步子走。每帧把真实经过的时间放进一个“蓄水池”（累加器），池子里够一个 `h` 就舀一勺出来仿真，剩下的留到下一帧。

这样：

- 仿真步长永远是 `h`，弹簧、碰撞、角色控制看到的是稳定的 `dt`；
- 真实帧率可以是 30、60、144，仿真仍按 60 Hz 推进；
- 卡顿时可以在一帧里补几步，但要设上限，补不上就**主动放慢游戏**，而不是让一帧无限算下去。

### 4.2 数据与操作（先不看代码）

```
输入：dt（这一帧真实经过的秒数）、h（固定步长，本工程 1/60）
状态：accumulator（上一帧没消费完的时间，跨帧保留）

accumulator += dt
steps = 0
while accumulator >= h and steps < maxSteps:
    FixedUpdate(h)          // 物理、角色位移、AI
    accumulator -= h
    steps += 1
if steps == maxSteps:
    accumulator = 0         // 放弃追不上的时间
Update(dt)                  // 相机、动画、UI 等视觉更新
```

关键点：**`accumulator` 是跨帧保留的**。这一帧剩下的 `r` 不是丢掉，而是下一帧继续用。所以正确的时间账本是

```
accumulator_新 = accumulator_旧 + dt - steps * h
```

而不是每帧重新算 `dt - steps*h`。只有在“上一轮余数为 0 且没有触顶”时，`r = dt - steps*h` 才恰好落在 `[0,h)`；一旦触顶清零，这个式子就会给出错误结论。下面用表格走一遍。

### 4.3 三帧时间账本（可独立验算）

取 `h = 1/60 ≈ 0.0166667 s`，`maxSteps = 5`。

| 帧 | 进入时 acc | 本帧 dt | acc + dt | 执行步数 | 消费时间 | 离开时 acc | 说明 |
|---|---:|---:|---:|---:|---:|---:|---|
| 1 | 0 | 0.020 | 0.020 | 1 | 0.016667 | 0.003333 | 60 FPS 附近，正常 |
| 2 | 0.003333 | 0.033 | 0.036333 | 2 | 0.033333 | 0.003000 | 30 FPS，补了两步 |
| 3 | 0.003000 | 0.100 | 0.103000 | 5 | 0.083333 | 0（代码清零） | 卡顿 100 ms，触顶，丢弃 0.019667 s |
| 4 | 0 | 0.016667 | 0.016667 | 1 | 0.016667 | 0 | 回到正常 |

第 3 帧要注意两件事：

1. 代码把 `dt` 先夹到 `0.1 s`。如果真实卡了 200 ms，进入 `UpdateGameplay` 的 `dt` 也只有 0.1，**真实时间里已经有 0.1 s 没有被仿真**；
2. 5 步只消费 0.0833 s，还剩 0.019667 s；因为 `steps == maxSteps`，代码把累加器清零，这 0.019667 s 也被丢弃。

所以“长期平均仿真时间 = 真实时间”这句话**只在从不触顶、也从不被 `dt` 上限裁剪时成立**。一旦持续掉帧，本工程的设计选择是“游戏变慢”，而不是“无限补步”。这是有意的取舍，不是 bug。

### 4.4 为什么要清零，而不是保留余数

如果触顶后保留 `0.019667`，下一帧又会在已经很慢的基础上继续补，帧时间继续上升，可能永远追不上。清零等于承认“这一段时间追不回来了”，把游戏时间轴向后拨一点。玩家感受到的是慢动作，而不是卡死。

### 4.5 为什么还要 `Update(dt)`

不是所有东西都该按固定步长走：

- **物理、角色位移、AI 决策**：需要稳定步长，放 `FixedUpdate(h)`；
- **相机跟随、动画采样、UI、粒子外观**：用这一帧真实经过的时间更平滑，放 `Update(dt)`。

代价是两者用的 `dt` 不同：`FixedUpdate` 看到的是 `h`，`Update` 看到的是被夹过的帧时间。写代码时要清楚一个组件属于哪一类，不要在两个回调里对同一个物理量各积分一次。

### 4.6 本工程没有做的事：渲染插值

固定 60 Hz 仿真、144 Hz 渲染时，两帧渲染之间可能没有新的仿真状态。严格做法是保存上一帧和当前帧的仿真状态，按 `alpha = accumulator / h` 插值后再渲染：

```
renderPos = lerp(prevPos, currPos, accumulator / h)
```

本工程**没有实现**这一步。渲染直接用最近一次 `FixedUpdate` 之后的位置，因此角色位置最多滞后一个 `h`（约 16.7 ms）。相机每帧都跟随这个“稍旧”的位置，视觉上是否明显，取决于帧率和相机平滑；不能未经测量就说“看不出来”。这是已知取舍，不是“固定步长天然不需要插值”。

## 5. 回到本仓库源码

### 5.1 真实主循环

`engine/src/runtime/Engine.cpp` 的 `Engine::MainLoop`（节选，保留控制流，省略平台与编辑器分支）：

```cpp
// 源码节选：Engine::MainLoop
while (m_running) {
    Input::BeginFrame();                 // 1) 清“本帧刚按下”的边沿状态
    if (!m_window.Poll()) break;         //    收 Windows 消息
    Input::SetMouseState(...);
    Timer::Tick();                       // 2) 更新 Timer::Delta()
    AudioSystem::Get().Update(Timer::Delta());

    if (m_window.WasResized()) { ... }   // 3) 视口尺寸变化
    if (m_window.Width() == 0 || m_window.Height() == 0) continue;

    const float dt = (std::min)(Timer::Delta(), 0.1f);  // 4) 夹住 dt
    m_time += dt;

    ...                                  // 5) 冒烟/演示/开局逻辑
    UpdateGameplay(dt);                  // 6) 固定步长仿真 + 可变步长更新

    ...                                  // 7) 热键、相机、拾取、渲染、UI
    m_device.EndFrame(m_vsync);          // 8) Present
}
```

和你的 `while` 相比，多出来的步骤各有明确理由：

| 步骤 | 为什么需要 |
|---|---|
| `Input::BeginFrame` 在 `Poll` 之前 | 先把上一帧的“刚按下”清掉，再让本帧消息写入；顺序反了会丢一帧边沿或重复触发 |
| `Window::Poll` | Windows 的消息必须有人取，否则窗口无响应 |
| `Timer::Tick` | 把“现在”变成 `Delta()`，供本帧所有系统使用 |
| `AudioSystem::Update` 用原始 `Delta` | 音频是连续流，不希望被 0.1 s 的裁剪影响（它有自己的缓冲策略） |
| `dt = min(Delta, 0.1)` | 断点、拖窗口后不让一帧的步长无限大 |
| `UpdateGameplay(dt)` | 固定步长仿真 + 可变步长视觉更新 |
| `EndFrame` | 提交并 Present；VSync 在这里等 |

### 5.2 固定步长实现

```cpp
// 源码节选：Engine::UpdateGameplay
void Engine::UpdateGameplay(float dt) {
    const bool playing = m_showEditor ? m_editor.IsPlaying() : true;
    const bool paused  = m_showEditor ? m_editor.IsPaused()  : false;
    if (!playing || paused) return;

    m_accumulator += dt;
    int steps = 0;
    while (m_accumulator >= kFixedDt && steps < kMaxSubSteps) {
        m_world.FixedUpdate(kFixedDt);   // 物理/AI/角色
        m_accumulator -= kFixedDt;
        ++steps;
    }
    if (steps == kMaxSubSteps) m_accumulator = 0.0f;  // 防死亡螺旋
    m_world.Update(dt);                               // 相机/动画/UI
}
```

常量在文件顶部：

```cpp
constexpr float kFixedDt    = 1.0f / 60.0f;
constexpr int   kMaxSubSteps = 5;
```

注意 `UpdateGameplay` 在编辑器未运行（`!playing`）或暂停时直接返回，**累加器不会增长**。这避免在编辑器里摆场景时，一按运行就把暂停期间的时间一次性补出来。

### 5.3 调用链与数据流

```
main → Engine::Run
        └─ Engine::Init
        └─ Engine::MainLoop
             ├─ Input::BeginFrame / Window::Poll → Input 状态
             ├─ Timer::Tick → Timer::Delta()
             ├─ Engine::UpdateGameplay(dt)
             │    ├─ while acc >= h: World::FixedUpdate(h)
             │    │      └─ GameObject::FixedUpdate → Component::OnFixedUpdate
             │    └─ World::Update(dt)
             │           └─ GameObject::Update → Component::OnUpdate
             └─ Renderer::Render / Device::EndFrame
```

- `World::FixedUpdate` 和 `World::Update` 都先快照根节点列表，再遍历；这是防止组件在更新中生成/删除对象导致迭代器失效（见 `World.cpp` 注释）。
- `GameObject::FixedUpdate/Update` 只调用 `enabled` 的组件；组件通过虚函数 `OnFixedUpdate/OnUpdate` 接收时间。
- `Timer` 用 `double` 保存 `QueryPerformanceCounter` 换算出的绝对秒数，`Delta()` 再转 `float`。绝对时间用 `double` 是为了长时间运行不丢精度；单帧 `dt` 用 `float` 足够。

### 5.4 初始化与释放顺序

`Engine::Init` 的顺序（源码）：

```
Log → Timer → Input::BeginFrame → JobSystem → CoInitialize
    → Window → Device → Audio → Renderer → Assets → World（建关卡）
    → ImGui → Editor
```

`Engine::Shutdown` 基本相反（Audio 先关，然后 Editor → ImGui → World → Assets → Renderer → Device → Window → JobSystem → Log）。原因不是“仪式感”，而是依赖方向：`Renderer` 使用 `Device` 的资源，`Editor` 使用 `ImGui` 和 `Renderer`，任何“下层先销毁、上层还在用”的顺序都会在退出时崩。具体每一层为什么依赖下一层，见第 2 讲。

## 6. 把一帧走完：一个更小的例子

只跟踪一个角色，`speed = 5 m/s`，`h = 1/60 s`，从 `x = 0` 出发，忽略碰撞：

| 帧 | dt | 执行步数 | 每步位移 | 本帧位移 | 累计位置 | 剩余 acc |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 0.020 | 1 | 0.0833 | 0.0833 | 0.0833 | 0.00333 |
| 2 | 0.033 | 2 | 0.0833 | 0.1667 | 0.2500 | 0.00300 |
| 3 | 0.100 | 5 | 0.0833 | 0.4167 | 0.6667 | 0（触顶） |
| 4 | 0.0167 | 1 | 0.0833 | 0.0833 | 0.7500 | ≈0 |

验算：第 2 帧结束累计仿真时间 `0.016667 + 2×0.016667 = 0.05 s`，`5 m/s × 0.05 s = 0.25 m`，与表一致。第 3 帧真实过了 0.1 s，但只仿真了 0.0833 s，所以位置只到 `0.25 + 0.4167 = 0.6667 m`，而不是 `0.75 m`——差的部分就是被丢弃的时间。**这就是“卡顿后游戏变慢”在数字上的样子。**

## 7. 进阶：数学依据与工程取舍

### 7.1 显式欧拉为什么不无条件稳定

对一阶系统

```
ẋ = -k x        （k > 0，例如带阻尼的回弹）
```

显式欧拉：

```
x_{n+1} = x_n + h(-k x_n) = (1 - k h) x_n
```

要让 `x` 不增长，需要 `|1 - k h| < 1`，即

```
0 < h < 2/k
```

`k` 越大（弹簧越硬、反馈越强），允许的 `h` 越小。固定步长保证的是“每台机器用同一个 `h`”，**不保证这个 `h` 对你的 `k` 足够小**。如果 `k` 大到 `2/k < 1/60`，固定 60 Hz 仍然会发散；解决办法是减小 `h`、改半隐式/隐式积分，或给系统加阻尼，而不是“因为用了固定步长所以稳定”。

### 7.2 相位滞后与插值

固定步长把连续时间离散成 `t_n = n h`。渲染发生在任意时刻 `t`，最近一次仿真状态对应 `t_n ≤ t`，所以渲染看到的系统状态最多滞后 `h`。`h` 越小滞后越小，但每帧可能要多算几步，CPU 成本上升。插值能把视觉位置补到 `t`，代价是要保存前后两个状态，并处理“物体瞬移/传送”时不能插值的情况。本工程选择不插值，把复杂度留给后续。

### 7.3 为什么是 60 Hz

- 60 Hz 是常见显示器刷新率，输入到画面的延迟预算容易对齐；
- `h = 16.7 ms` 对教学级角色速度和碰撞尺寸足够小；
- 再高（120/240 Hz）会成倍增加物理/AI 的 CPU 开销，而本工程的物理是单线程简化模型，收益不明显。

这是**本工程的选择**，不是引擎的通用常数。竞技射击可能用 128 tick，物理重负载项目可能用 30 Hz + 插值，取决于仿真成本与手感要求。

### 7.4 取舍清单

| 选择 | 代价 | 本工程为什么接受 |
|---|---|---|
| 固定 60 Hz | 高 stiffness 系统仍可能不稳 | 教学级弹簧参数范围内够用 |
| 最多 5 子步 | 持续掉帧时游戏变慢 | 避免死亡螺旋，行为可预测 |
| `dt` 夹到 0.1 s | 断点/拖动窗口期间的真实时间丢失 | 防止一帧瞬移穿墙 |
| 不做渲染插值 | 高刷屏上位置更新有 60 Hz 台阶 | 降低“位置为什么是这个值”的理解成本 |
| 物理单线程 | 大量刚体时 CPU 成为瓶颈 | 教学规模；并行见第 20 讲 |

## 8. 实验

以下命令来自 `Engine` 的参数解析；本环境是 Linux，**没有运行 Windows exe**，所以只给预期观察，不伪造日志。

1. **看固定步长的位移**
   ```bat
   build\bin\ErMao.exe --smoke --frames 200 --level thirdperson
   ```
   `--smoke` 会在第 30~120 帧模拟按 W，并在第 30/60/120/180 帧打印玩家位置（`[冒烟] 帧 … 玩家位置 …`）。
   预期：位置按固定步长逐步变化；第 120 帧之后脚本不再按 W，速度应逐渐归零（可能还有少量惯性/摩擦位移）。若位置在第 120 帧后仍持续大幅增加，先查 `ThirdPersonController::OnFixedUpdate` 是否还在读模拟输入。

2. **看掉帧后的“变慢”**
   在 `Engine::UpdateGameplay` 临时加一行日志，打印 `dt`、`steps`、`m_accumulator`；用调试器在循环里停 300 ms，或拖动窗口制造卡顿。
   预期：`steps` 达到 5、`m_accumulator` 被清零；这一帧仿真时间小于真实时间。若 `steps` 超过 5，说明 `kMaxSubSteps` 的修改没生效或被别的分支绕过。

3. **看 `dt` 上限**
   在 `UpdateGameplay` 入口打印 `dt`，制造一次 500 ms 的卡顿。
   预期：打印值最多 `0.1`，不会出现 `0.5`。若出现，检查是否有人绕过了 `std::min(Timer::Delta(), 0.1f)` 直接调用 `UpdateGameplay`。

4. **看 144 Hz 下的位置台阶（需要高刷屏）**
   把渲染帧率限到 144（或关闭 VSync 并观察高 FPS），让角色匀速走，贴近看角色与背景的相对运动。
   预期：位置每约 16.7 ms 才更新一次，可能出现轻微台阶；相机跟随会掩盖一部分。这个实验**依赖显示器和相机参数**，看不到台阶不代表没有滞后。

排查入口：固定步长相关问题先看 `UpdateGameplay`，再看具体组件的 `OnFixedUpdate` 是否误用了 `OnUpdate` 的 `dt`，最后看 `kFixedDt/kMaxSubSteps` 是否被改过。

## 9. 常见错误

| 错误 | 后果 | 本工程怎么处理 |
|---|---|---|
| 物理用 `Update(dt)` 的可变步长 | 不同帧率下手感/稳定性不同 | 物理放 `FixedUpdate(kFixedDt)` |
| 累加器每帧清零 | 余数丢失，仿真时间系统性偏少 | 跨帧保留，只在触顶时清零 |
| 触顶后继续保留积压 | 死亡螺旋，越卡越补 | `if (steps == kMaxSubSteps) m_accumulator = 0` |
| `dt` 不夹上限 | 断点/拖窗口后一帧瞬移、穿墙 | `min(Timer::Delta(), 0.1f)` |
| 用 `float` 存绝对时间 | 长时间运行精度下降 | `double` 存 `Now()`，单帧转 `float` |
| 认为“固定步长 = 一定稳定” | 高刚度系统仍发散 | 稳定条件 `h < 2/k`，参数要匹配 |
| 在 `FixedUpdate` 里做相机平滑 | 相机按 60 Hz 跳，和渲染不同步 | 相机/动画放 `Update(dt)` |

## 11. 练习（故意改坏）

1. 把 `kMaxSubSteps` 从 5 改成 50：**预期**卡顿后能补更多步，但一帧可能算 50 步，帧时间更长；观察是否更容易触发下一次卡顿。
2. 把 `std::min(Timer::Delta(), 0.1f)` 改成 `1.0f`：**预期**断点/拖动窗口后角色瞬移，甚至穿墙；这是验证 `dt` 上限作用的最直接实验。
3. 把 `while` 改成 `if`：**预期**低帧率下仿真时间小于真实时间，游戏整体变慢，但不会补步；对比 §6 的表，位置会小于理论值。
4. 把 `m_accumulator = 0` 那行删掉：**预期**长时间卡顿后积压越来越多，帧时间持续上升（死亡螺旋）。
