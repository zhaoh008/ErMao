# 第 7 讲：后处理与色彩——HDR、色调映射与 Gamma

> 对应 GAMES104 第 7 讲（渲染管线与后处理）。
> 代码：`engine/shaders/Post.hlsl`、`engine/src/renderer/Renderer.cpp` 的 `PostPass`、`engine/src/rhi/RenderTarget.cpp` 与 `engine/src/rhi/Device.cpp`（缓冲格式）。
> 目标：解释“为什么太阳和高光会一片纯白、暗部会死黑、加色会发灰”，以及 HDR 缓冲、曝光、ACES、gamma 各自解决哪一段。

---

## 0. 太阳一片纯白，暗部死黑

把相机对着太阳附近，画面里太阳和金属高光是一块没有细节的纯白；转到背光面，暗部又黑成一片，和照片里“亮部有层次、暗部还能看出材质”的感觉不一样。这不是“亮度没调对”，而是**显示器的动态范围**和**渲染结果的动态范围**不匹配：

- 太阳、镜面高光的线性亮度可以到 10、18 甚至更高；
- 8 位后备缓冲只能存 `[0,1]` 的 256 档，超过 1 的部分只能截断；
- 显示器的 sRGB 编码又要求把线性值做一次非线性压缩。

本讲按“先直接画到 8 位缓冲 → 看它怎么坏 → 换成 HDR 缓冲 + 曝光 + ACES + gamma”的顺序走。第 5、6 讲算出的 `color` 都是线性值，本讲负责把它变成能显示的像素。

---

## 1. 最简版本：直接画到 8 位后备缓冲

最省事的做法是像素着色器算完直接返回，让 8 位后备缓冲自己截断：

**概念伪代码（不是本工程源码）**

```hlsl
float3 color = ShadePixel(...);   // 线性值，可能 > 1
return float4(color, 1.0);        // RTV 是 UNORM，硬件把结果 clamp 到 [0,1]
```

它能让画面“出来”，但会同时制造下面四个问题。

### 1.1 高光截断：亮的全变白

太阳盘在 `Sky.hlsl` 里乘了 18，金属高光在掠射角也可能远超 1。写进 `R8G8B8A8_UNORM` 时，所有 `>1` 的值都变成 `1.0`：

```
太阳盘 18.0  ─┐
高光   3.2   ─┼─▶ clamp 到 1.0 ─▶ 同一块纯白，失去所有层次
地面   0.8   ─┘
```

结果是“亮部一片糊”，你没法从画面判断高光到底有多亮，也没法在后期把曝光拉回来——信息已经丢了。

### 1.2 暗部色带：8 位线性存储不够用

8 位缓冲把 `[0,1]` 均分成 256 份，最暗的非零值是 `1/255 ≈ 0.0039`。线性亮度 `0.002` 在这种缓冲里只能存成 0 或 1，暗部渐变会出现一条条色带。更糟的是人眼对暗部差异很敏感，色带在暗部最明显。

### 1.3 加色变灰：在编码空间相加

如果直接在 8 位缓冲里做加法混合（例如两个半透明亮片叠加），每个像素存的是**编码值**，不是线性值。两个线性 `0.6` 的亮片：

```
正确（线性相加）：0.6 + 0.6 = 1.2 → 色调映射 → 仍有颜色层次
错误（编码后相加）：encode(0.6)≈0.79，0.79+0.79=1.58 → clamp 1.0
```

编码空间相加会更快撞到 1，结果是一片发白、发灰，颜色也被洗掉。本工程的粒子是加法混合到 `RGBA16F` 的线性场景缓冲里，避开了这个问题；但任何“直接画到 8 位后备缓冲”的路径都会踩到。

### 1.4 曝光不可调：只能回去改灯

直接画到后备缓冲时，想让画面暗一点，只能改太阳强度、环境光强度或材质 albedo——那是在改**场景**，不是在改**相机**。真实相机调的是曝光（光圈/快门/ISO），它应该只影响“进多少光”，不影响场景本身。

## 2. HDR 缓冲：先把信息留住

**HDR（High Dynamic Range，高动态范围）**在这里的意思很具体：场景颜色先写进一张**浮点**纹理，值可以大于 1，先不截断；等所有光照、天空、粒子都画完，再统一决定怎么压到 `[0,1]`。

本工程用 `DXGI_FORMAT_R16G16B16A16_FLOAT`（RGBA16F，每通道 16 位浮点）作为场景颜色缓冲：

**源码节选（`Renderer::EnsureSceneTarget`）**

```cpp
const bool ok = m_sceneTarget.Create(m_device->GetDevice(), width, height,
                                     DXGI_FORMAT_R16G16B16A16_FLOAT, true);
```

`true` 表示同时创建深度缓冲。`RenderTarget::Create` 里颜色纹理的 `BindFlags` 是 `RENDER_TARGET | SHADER_RESOURCE`，深度用 `R32_TYPELESS`（DSV `D32_FLOAT`、SRV `R32_FLOAT`）。

整条链路上有三种不同用途的缓冲，别混：

| 缓冲 | 格式 | 作用 |
|---|---|---|
| 场景颜色 `m_sceneTarget` | `R16G16B16A16_FLOAT` | 光照结果，线性、可 >1 |
| 视口 `m_viewportTarget` | `R8G8B8A8_UNORM` | Post 的输出，已 gamma 编码，供编辑器/拷贝 |
| 后备缓冲 | `R8G8B8A8_UNORM` | 最终显示（`Device.h` 的 `m_format`） |

16 位浮点的动态范围远大于 8 位定点，但它也不是无限的：half float 的最大值约 65504，尾数只有 10 位，约 3 位十进制精度。对本工程的太阳/高光足够，但不要把它当成“任意精度”。

## 3. 曝光：在色调映射之前乘

曝光是一个乘法，放在读场景颜色之后、ACES 之前：

**源码节选（`engine/shaders/Post.hlsl`，`PSMain` 开头）**

```hlsl
float3 hdr = gSceneColor.Sample(gLinearSamp, uv).rgb * gParams.x;
```

`gParams.x` 来自 CPU 的 `m_exposure`（`PostCB params.params = Vec4(m_exposure, 0.0f, 1.2f, ...)`），编辑器“渲染 → 曝光”滑块的默认值是 `1.0`，范围 `0.2~3.0`（`EditorUI.cpp`）。

曝光放在 tone mapping **之前**很关键：它改变的是“进入压缩曲线的位置”，而不是简单地把最终像素调亮。同一个 ACES 曲线，曝光 1.0 和 2.0 对高光的压缩比例不同，所以调曝光能看到“亮部层次变化”，而不是整体加一个常数。

> 本工程是**固定曝光**，没有自动曝光/人眼适应。`frame.ambientDownExposure.w` 里虽然存了 `m_exposure`，但 `PBR.hlsl` 只读它的 `rgb`，曝光实际只在 `Post.hlsl` 里生效。

## 4. ACES 色调映射

**色调映射（Tone Mapping）**是把 HDR 的 `[0,∞)` 压到显示器 `[0,1]` 的曲线。它要满足：`T(0)=0`；高光平滑压缩、不直接截断；中间调尽量保持明暗关系。本工程用 Narkowicz 对 ACES（Academy Color Encoding System）的参考渲染变换（RRT）与输出变换（ODT）做有理函数拟合：

**源码节选（`engine/shaders/Post.hlsl`，`ACESFilm`）**

```hlsl
float3 ACESFilm(float3 x)
{
    const float a = 2.51;
    const float b = 0.03;
    const float c = 2.43;
    const float d = 0.59;
    const float e = 0.14;
    return saturate((x * (a * x + b)) / (x * (c * x + d) + e));
}
```

它的几个性质可以直接算出来：

- `x=0` 时分子为 0，`T(0)=0`；
- `x→∞` 时分子/分母都按 `x²` 增长，极限是 `2.51/2.43 ≈ 1.0329`，再被 `saturate` 截到 1；
- `T(1) = (2.51+0.03)/(2.43+0.59+0.14) = 2.54/3.16 ≈ 0.8038`：线性 1.0 并不会映射到显示 1.0，而是约 0.80；
- 有理函数在 `x≈7.24` 处达到 1，再往上 `saturate` 会截断。也就是说，**极高光仍然会丢失细节**，只是损失被推到了很远的地方，不像直接 clamp 那样在 1.0 就截断。

`saturate` 把结果夹到 `[0,1]`；`x≥0` 时分母 `x(2.43x+0.59)+0.14` 恒为正，不存在除零问题。本工程的着色结果不会是负的，但粒子/自发光叠加可能产生很大的值。

## 5. Gamma：为什么最后要开方

显示器和 sRGB 纹理按非线性编码存储亮度，近似关系是 `encoded ≈ linear^(1/2.2)`。原因很实际：人眼对暗部差异更敏感，把更多码值分配给暗部，8 位也不容易出现暗部色带。

本工程的策略是“**光照全程线性，最后只编码一次**”：

1. 贴图以 `_SRGB` 格式创建（`Texture::CreateFromFile(..., srgb=true)`），硬件采样时自动解码成线性；
2. 编辑器里选的 `albedo` 直接按线性值使用（`PBR.hlsl` 里有注释说明）；
3. 场景缓冲 `RGBA16F` 存线性值；
4. `Post.hlsl` 在 ACES 之后做一次 `pow(color, 1/2.2)`，写入 `R8G8B8A8_UNORM` 的视口/后备缓冲。

**源码节选（`Post.hlsl`，`PSMain` 结尾）**

```hlsl
float3 mapped = ACESFilm(hdr);
float2 d = uv - 0.5;
float vignette = 1.0 - dot(d, d) * gParams.z;   // gParams.z = 1.2
mapped *= saturate(vignette);
mapped = pow(mapped, 1.0 / 2.2);
return float4(mapped, 1.0);
```

暗角（vignette）在 ACES 之后、gamma 之前：它乘的是 `[0,1]` 的显示线性值，屏幕角落最暗到 `1 - 0.5×1.2 = 0.4`。

为什么后备缓冲用 `UNORM` 而不是 `_SRGB`？因为 `Device.h` 里 `m_format = DXGI_FORMAT_R8G8B8A8_UNORM`，`RenderTarget` 的视口也是 `R8G8B8A8_UNORM`（`colorSrgb` 参数默认 `false`）。**gamma 是在 shader 里手动做的**；如果哪天把后备缓冲改成 sRGB 视图，又保留 `pow(1/2.2)`，就会双重编码，画面变灰。反过来，如果忘了 `pow`，线性值被显示器当 sRGB 显示，整体会偏暗。

`pow(1/2.2)` 是 sRGB 分段曲线的近似；精确 sRGB 在暗部有一段线性段，两者在小值处略有差别，但工程上通常够用。

## 6. 后处理 Pass 与全屏三角形

**源码节选（`Renderer::PostPass`）**

```cpp
if (!target) target = m_device->GetBackbufferRTV();
ctx->OMSetRenderTargets(1, &target, nullptr);
params.params = Vec4(m_exposure, 0.0f, 1.2f, m_debugView == 5 ? 2.0f : 0.0f);
params.screen = Vec4(width, height, 1.0f / width, 1.0f / height);
m_postParams.Update(ctx, params);

RenderStates::SetDepthNone(ctx);       // 全屏、无深度
RenderStates::SetBlendOpaque(ctx);     // 不混合
RenderStates::SetCullNone(ctx);        // 不剔除
m_postShader.Bind(ctx);
ID3D11ShaderResourceView* srv = m_sceneTarget.ColorSRV();
ctx->PSSetShaderResources(0, 1, &srv); // 场景颜色
Texture::BindSampler(ctx, 0, D3D11_FILTER_MIN_MAG_MIP_LINEAR, D3D11_TEXTURE_ADDRESS_CLAMP);
ctx->IASetInputLayout(nullptr);
ctx->IASetPrimitiveTopology(D3D11_PRIMITIVE_TOPOLOGY_TRIANGLELIST);
ctx->Draw(3, 0);
```

后处理不需要顶点缓冲：顶点着色器用 `SV_VertexID` 生成覆盖全屏的三角形：

**源码节选（`Post.hlsl`，`VSMain`）**

```hlsl
float2 uv = float2((vertexId << 1) & 2, vertexId & 2);
o.clip = float4(uv * float2(2.0, -2.0) + float2(-1.0, 1.0), 1.0, 1.0);
o.uv = uv;
```

`vertexId=0,1,2` 对应 UV `(0,0)、(2,0)、(0,2)`，裁剪空间是 `(-1,1)、(3,1)、(-1,-3)`，正好盖住屏幕；`o.uv` 在屏幕范围内插值出 `[0,1]²`。这比“两个三角形 + 顶点缓冲”少一次绑定，也没有对角线接缝。

`PostPass` 的输出目标是 `outputRtv`：编辑器路径是 `m_viewportTarget`（RGBA8）；无编辑器路径也先写 `m_viewportTarget`，再由 `CopyPass` 用点采样器拷贝到后备缓冲，保证两条路径的颜色管线一致。`CopyPass` 只做拷贝，不再做 gamma。

调试视图 5 是一个例外：`Post.hlsl` 在 tone mapping 之前直接返回阴影贴图深度：

```hlsl
if (gParams.w > 1.5) { float d = gShadowTex.Sample(gLinearSamp, uv).r; return float4(d.xxx, 1.0); }
```

这段 shader 不经过 ACES/gamma，所以看起来会比正常画面暗一些；但 `PostPass` 只绑定了场景颜色到 `t0`，没有把 `m_shadowMap` 绑到 `gShadowTex` 的 `t1`，因此当前这条视图取不到阴影深度，是一个待修复的缺口，不能当正常画面调色参考。`gScreen` 虽然在 CPU 侧填了分辨率，但当前 `Post.hlsl` 并没有使用它。

## 7. 一个像素走完管线

取场景缓冲里的一个像素，线性值为 `(4.0, 1.0, 0.25)`，曝光 `1.0`：

| 通道 | 线性 HDR | ACES 后 | gamma 后 | 8 位 |
|---|---|---|---|---|
| R | 4.0 | `(4×(2.51×4+0.03))/(4×(2.43×4+0.59)+0.14) = 40.28/41.38 ≈ 0.9734` | `0.9734^(1/2.2) ≈ 0.9878` | 252 |
| G | 1.0 | `2.54/3.16 ≈ 0.8038` | `0.8038^(1/2.2) ≈ 0.9055` | 231 |
| B | 0.25 | `0.164375/0.439375 ≈ 0.3741` | `0.3741^(1/2.2) ≈ 0.6396` | 163 |

最终像素约 `(252, 231, 163)`：一个偏暖、但仍保留了红绿蓝比例的高光。

对比“直接 clamp 到 8 位再 gamma”：

```
clamp 后 (1.0, 1.0, 0.25) → gamma (1.0, 1.0, 0.532) → (255, 255, 136)
```

红绿都被推到 255，蓝色只剩 136，高光变成刺眼的黄白色；ACES 把红绿压得更多、蓝相对保留，所以高光更接近“照片里的暖白”。这就是色调映射“保留高光层次”的具体含义。

再看暗部：线性 `0.002` 在 8 位线性缓冲里只能存成 0 或 1（最暗非零值 `1/255≈0.0039`）；在 HDR 缓冲里它可以保留，经 ACES 后约 `0.000496`，gamma 后约 `0.0315`，即 8/255。也就是说，暗部信息是在**压缩时**丢的，不是一开始就被 8 位量化丢掉的。

本环境是 Linux，**没有运行 exe，也没有生成截图**。以下命令与现象是条件性预期。

```bat
build\bin\ErMao.exe --level thirdperson --play --frames 120
build\bin\ErMao.exe --level thirdperson --play --noeditor --frames 120 --screenshot tone-default.png
```

本工程**没有** `--exposure` 命令行参数；曝光只能在编辑器“渲染 → 曝光”里调，或改 `m_exposure` 的默认值。

1. 在编辑器“渲染 → 曝光”里把 `1.0` 调到 `2.0`：整体变亮，但太阳/高光不会立刻变成更大的纯白块，因为 ACES 会把高光压回来；如果只是把太阳强度乘 2，亮部面积和颜色都会明显变化——这两种“变亮”不是一回事；
2. 把曝光调到 `0.2`：整体变暗，暗部色带会比 8 位直接渲染少，因为中间过程是 RGBA16F；但最终输出仍是 8 位，极端暗部仍可能看到色带；
3. `--screenshot` 截的是后备缓冲，已经过 `CopyPass`，所以截图颜色应与窗口一致；如果截图偏暗/偏灰，先检查是不是在 shader 里多乘了一次 gamma，而不是先怀疑曝光；
4. 调试视图 5 按 shader 意图是看阴影贴图，但当前 `PostPass` 没绑定 `t1`，实际不可用；即便绑定，它也绕过 ACES/gamma，灰度和正常画面不可比。

不符合预期时的排查入口：整屏纯白，检查 `m_exposure` 是否被设得过大、ACES 是否被误删；整屏过暗，检查是否漏了 `pow(1/2.2)` 或把 `_SRGB` 贴图又解码了一次；高光出现硬边，检查是不是直接 clamp 到 8 位而不是走 ACES；颜色发灰，检查是否双重 gamma（sRGB 后备缓冲 + 手动 pow）。

## 10. 常见错误

| 错误 | 后果 |
|---|---|
| 直接写 8 位后备缓冲、不做 tone mapping | 高光一片纯白，暗部色带 |
| 先 gamma 再 ACES | 曲线作用在编码值上，中间调和高光比例都不对 |
| sRGB 后备缓冲 + shader 里又 `pow(1/2.2)` | 双重编码，画面发灰、对比度变低 |
| `_SRGB` 贴图采样后又手动解码 | 同上，颜色变暗发灰 |
| 曝光放在 ACES 之后 | 只是整体缩放显示值，无法改变高光压缩比例 |
| 认为 ACES 能把所有高光都保留 | 它在 `x≈7.24` 后仍会 saturate 到 1，极高光会截断 |
| 把调试视图 5 当正常画面调色 | 它不经过 ACES/gamma，颜色不可比 |

## 11. 自测题

1. 为什么 `albedo` 要在线性空间参与光照？举“两盏灯”的例子说明 gamma 空间相加的错误。**答**：光照是能量相加，线性空间才满足 `L1+L2`；若在编码空间相加，`encode(0.5)+encode(0.5)=1.46` 会提前饱和，颜色和亮度都错。
2. ACES 曲线 `x→∞` 的极限是多少？这说明什么？**答**：有理函数极限是 `2.51/2.43≈1.0329`，再被 `saturate` 截到 1；它是有界的，但 `x≈7.24` 之后仍会饱和，极高光会丢细节。
3. 场景 RT 用 `RGBA8_UNORM` 而不是 `RGBA16F`，会丢失什么？**答**：大于 1 的高光信息（被截断）和暗部精度（线性 8 位最暗非零约 0.0039），色带和死白都会出现。
4. 全屏三角形的 UV 公式 `(vertexId<<1)&2` 怎么覆盖 `[0,1]²`？**答**：三个顶点得到 `(0,0)、(2,0)、(0,2)`，裁剪空间是 `(-1,1)、(3,1)、(-1,-3)`，三角形覆盖屏幕，UV 在屏幕内插值到 `[0,1]`。
5. 本工程在哪里做 gamma？为什么只做一次？**答**：`Post.hlsl` 末尾 `pow(mapped,1/2.2)`；贴图在 `_SRGB` 采样时已解码，后备缓冲是 `UNORM`，所以只在最终输出编码一次。

## 12. 练习（故意改坏）

1. 把 `Post.hlsl` 最后的 `pow(mapped, 1.0/2.2)` 删掉：**预期**画面整体变暗（线性值被显示器当 sRGB 显示），暗部更黑。
2. 把 `m_exposure` 的默认值从 `1.0` 改成 `4.0`（超过 UI 的 3.0 上限，需要改代码）：**预期**整体变亮，但高光不会像“直接乘 4 再 clamp”那样整块死白；对照两种做法的太阳边缘能看到 ACES 的压缩。
3. 把场景 RT 从 `R16G16B16A16_FLOAT` 改成 `R8G8B8A8_UNORM`：**预期**太阳/高光处死白，暗部出现色带；注意还要同时改 `EnsureSceneTarget` 的格式，否则只是改注释。
